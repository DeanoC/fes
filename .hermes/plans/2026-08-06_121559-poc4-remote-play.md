# POC4 Remote Play Design and Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Prove a measured, standalone remote-play vertical slice from real MiSTer HDMI output to a host capture device, through low-latency H.264/RTP transport, to an independent receiver/display, while explicitly deferring physical glass-to-glass latency until the hardware measurement setup is available.

**Architecture:** Keep MiSTer/Main_MiSTer, the POC2 cache/launch path, and the POC3 host API unchanged initially. The existing host-side `remote-play-spike` remains the sender boundary: AVFoundation captures a real UVC HDMI device, VideoToolbox encodes H.264, and the sender packetizes media over RTP while using its authenticated control channel for session/report/stop signaling. Add an independent receiver/display harness as the next vertical slice, then integrate only after standalone evidence is green. Treat all physical claims separately from software/protocol claims.

**Tech Stack:** Go 1.26.5, macOS AVFoundation/CoreMedia/CoreVideo/VideoToolbox, H.264, RTP RFC 6184, UDP media transport, authenticated TCP control channel, independent receiver/display implementation, JSON evidence reports.

## Scope

### In scope

1. Establish a reproducible POC4 run identity and redacted evidence layout.
2. Validate the real capture device and actual source mode.
3. Build an independent receiver that can authenticate the control session, receive RTP/H.264, decode, display, and report packet/frame/keyframe/recovery behavior.
4. Prove a clean wired run with sender and receiver telemetry.
5. Run controlled packet loss/reordering experiments and characterize recovery.
6. Exercise session start, report, stop, and stale-generation rejection without exposing tokens or private paths.
7. Produce a go/no-go decision for later integration with the POC3 session/API.

### Explicitly deferred

- Physical glass-to-glass latency measurement; track separately in the GitHub issue created with this plan.
- Audio transport and A/V synchronization unless the receiver spike demonstrates a clear need for a separate follow-up.
- WebRTC, WAN/internet transport, TLS/public exposure, remote administration, and arbitrary clients.
- Target-side video decoding or changes to Main_MiSTer.
- POC2 cache/launch redesign.
- Full UI integration.

## Design decisions

### Media path

`MiSTer HDMI -> UVC capture device -> macOS AVFoundation -> VideoToolbox H.264 -> RFC 6184 RTP/UDP -> independent receiver -> decoder/display`.

The sender must use only real captured frames. No synthetic fallback is acceptable for hardware acceptance. The capture callback timestamp remains the source timestamp for sender metrics. The bounded one-frame queue remains the backpressure boundary; drops must be counted rather than hidden.

### Control path

Use the existing authenticated control protocol for `MEDIA_HELLO`, periodic `MEDIA_REPORT`, `PING`, `KEYFRAME_REQUEST`, and `STOP`. Keep session and generation identifiers distinct. Do not print or persist bearer/session secrets. Receiver reports must identify the run and generation but contain no target address, token, ROM name, device serial, or private filesystem path.

### Receiver boundary

Implement the smallest independent receiver that can:

- authenticate the control handshake;
- bind the configured RTP endpoint;
- validate RTP version, payload type, SSRC, sequence, timestamps, marker bits, and FU-A reassembly;
- depacketize H.264 access units and decode/display them using a documented macOS backend;
- report packet gaps, incomplete/corrupt access units, decode failures, decoded FPS, first-frame time, keyframe age, and clean shutdown;
- reject stale session/generation/control messages.

The receiver must not be coupled to the host API or target agent in the first slice. A test-only loopback source may be used for protocol tests, but hardware acceptance requires the real capture chain.

### Evidence boundary

Every run produces a local, ignored directory such as `artifacts/remote-play/<run-id>/` containing redacted sender and receiver JSON plus a short operator checklist. Reports classify each gate as `passed`, `failed`, or `untested`. Software tests are not hardware evidence; sender metrics are not receiver loss evidence; network timings are not physical latency.

## Acceptance gates

### G1 — software/protocol gate

`go test ./...`, `go test -race ./...`, `go vet ./...`, focused sender/receiver tests, and command/build tests pass. RTP/H.264 framing, authentication, malformed input handling, bounded queues, metrics, and stale-generation behavior are covered.

### G2 — real capture gate

A named physical UVC device opens and reports actual resolution/FPS. The selected mode is recorded. Missing device, permission failure, unsupported mode, and native startup failure are explicit failures—not skips in a claimed hardware run.

### G3 — receiver decode/display gate

The receiver obtains SPS/PPS + IDR, displays decoded frames, and records first-frame and steady-state metrics. A receiver that merely binds UDP is insufficient.

### G4 — clean wired-session gate

Run at least ten minutes over the approved wired path. Record sender and receiver telemetry, packet/frame/keyframe counts, queue high-water, drops, decode failures, and shutdown reason. Compare measured results against the existing target values: encode p95 <=8 ms and clean wired media drop rate <0.5%; mark unmeasured values untested.

### G5 — controlled impairment/recovery gate

Use a controlled loopback or network impairment harness to inject loss and reordering. Record receiver packet gaps, corrupted access units, recovery time, and keyframe age. Verify behavior with the current periodic-IDR limitation; do not claim instant keyframe recovery.

### G6 — lifecycle/security gate

Start/stop, control reconnect, duplicate/stale generation, malformed control messages, and secret redaction behave deterministically. The sender and receiver terminate without leaked goroutines/processes or unbounded buffers.

### G7 — deferred physical-latency gate

**UNTESTED / DEFERRED.** When the hardware setup is available, use a deterministic flashing/timestamp fixture and a high-speed camera or photodiode. Measure glass-to-glass p50/p95, document methodology, and compare with target p95 <=120 ms (stretch <=80 ms). No software timestamp may substitute for this gate.

### Task 4: Add the independent macOS decoder/display harness

**Files:**
- Create/modify: receiver command under `cmd/remote-play-receiver/` and macOS decoder/display adapter

Use the smallest documented macOS decode/display mechanism available in the repository/toolchain. Make display and decoder failures explicit. Keep the receiver independently runnable and avoid POC3 API coupling.

**Files:**
- Create/modify: `scripts/remote-play/`, `scripts/tests/remote-play_test.sh`, report helpers

Add deterministic run setup, receiver telemetry capture, and controlled loss/reordering injection. Ensure generated reports are ignored and privacy-scanned. Do not commit device serials, IPs, tokens, ROM names, or content digests.

Run script syntax/tests and a local loopback impairment experiment.

### Task 6: Execute the physical capture/decode/wired-session gates

**Files:**

With the real MiSTer HDMI source and capture device available, run G2, G3, G4, and G5. Ask the operator only for physical observations that cannot be observed through tools. Do not claim a gate from a bound socket or sender-only report.

### Task 7: Make the integration decision

| Area | Required evidence |

| Build | sender and receiver binaries build with Go 1.26.5 |
| Unit/race | `go test ./...`, `go test -race ./...`, focused receiver tests |
| Static | `go vet ./...`, `git diff --check` |

| Decode | receiver displays SPS/PPS + IDR and reports decoded frames |
| Wired run | ten-minute sender + receiver reports |
| Impairment | controlled gaps/recovery/keyframe-age report |
| Security | no secrets/private paths/device serials in committed artifacts |
| Physical latency | deferred GitHub issue; later fixture-based measurement |

## Risks and tradeoffs

- **Receiver backend choice:** keep it macOS-local and minimal; avoid committing to a cross-platform media stack before the first proof.
- **Periodic IDR only:** recovery may be delayed; measure and document rather than hiding the limitation.
- **UDP loss:** sender metrics cannot prove receiver loss; receiver telemetry is mandatory.
- **Audio:** defer until video transport is proven to avoid coupling independent failure modes.
- **Physical latency:** explicitly deferred and tracked separately; it is not evidence that POC4 is fully accepted.
- **Hardware availability:** if G2 cannot be run, report G2/G3/G4/G5 as untested rather than substituting loopback results.

## Out of scope for this plan

- Modifying Main_MiSTer or FPGA cores
- Replacing the POC2 target cache/launch architecture
- WAN/WebRTC/TLS/public service
- Full UI integration
- Audio synchronization
- Physical glass-to-glass latency measurement
