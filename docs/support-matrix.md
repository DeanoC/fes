# Core support matrix

Maintained source: [`support-matrix.json`](support-matrix.json). Regenerate this page with `python3 docs/support-matrix.py --write` from the repository root. ABI, interfaces and package standing stay in [core status](core-status.md). How to build a core stays in [misteross cores](../sources/misteross/docs/cores.md).

This page is the board and toolchain matrix. It is taken from `config/core-recipes.toml`, `config/core-library.toml`, `profiles/native-integration-dev.toml`, the per-core `toolchain.lock` files, the misteross producers, and the docs those files point at. A cell that is not in those sources is marked unverified or TBD.

The bootstrap image installs `fes.menu` and the pinned splash bitstream. Every playable core is a catalog install. Library standing `supported` is not a claim that the current bitstream has kit acceptance. Dated notes under `docs/validation/` accept only the artifact they name.

Tier 1 stays catalog `supported` (policy: Deano 2026-10-29). The tier names follow the tree. They do not use "HIL-verified and shipped in the default image" as Tier 1, because no playable core is in that image and kit notes do not move forward onto a new bitstream.

## Toolchain policy

Labels follow the accepted Quartus policy in [Quartus-built cores](design/quartus-cores.md) (issue #1163). `oss` is the Debian-style main set: Yosys + nextpnr-mistral. `quartus` is the non-free set: a proprietary toolchain. A core build is supposed to say which one made it, so an all-OSS selection can exclude every Quartus build. `FES_OSS_ONLY` is not implemented. Current registered recipes and package selection build the OSS lane only. A failed OSS route never falls back to Quartus.

Both labelled builds ship only when the published rule is met, on the same RTL and the same target clocks. Either every Quartus sign-off seed closes a required clock that an OSS sign-off seed misses, or the best complete-seed Fmax is at least 15% higher on any required clock: `100 × (Quartus best − OSS best) / OSS best`. Otherwise the core ships OSS only. No registered recipe declares a `toolchains` list yet, so no core ships both builds today. The i386 far-transfer numbers (about 40%) remain the worked example of a gap large enough for that rule. i386, pc386 and PC/XT are separately Quartus-primary; their nextpnr builds are advisory.

DE25-Nano (Agilex 5) is Quartus-only (policy); shell pending. policy: Deano 2026-10-29. Agilex 5 has no OSS reverse-engineering, so there is no OSS toolchain for that device. nextpnr-mistral targets Cyclone V (`5CSEBA6U23I7` in [the DE10-Nano board note](../sources/misteross/boards/de10nano/README.md)). Quartus Pro 24.1 or later is the first release that supports Agilex 5 ([Quartus-built cores](design/quartus-cores.md)). `sources/misteross/boards/de25nano` may be absent or present; the checker treats that landing as expected. Per-core DE25 cells stay on the policy line until the shell is on this branch and those cells are re-verified.

i386, pc386 and PC/XT use Quartus (primary, policy). policy: Deano 2026-10-29. nextpnr builds are advisory, and a nextpnr miss there is filed as a nextpnr issue, not a blocker. The checked-in producers remain the OSS diagnostic for PC/XT, pack-only nextpnr synthesis for pc386, and the Quartus 17.0.2 fit of the same Yosys netlist for i386 ([i386 CPU design](../sources/misteross/docs/i386-cpu-design.md), DeanoC/nextpnr#300). Those tree facts do not change the primary label.

ColecoVision still uses the old media handling and shows 0 titles. Updating that handling is low priority and is folded into the wider Coleco work (for example Adam support). policy: Deano 2026-10-29. The checked-in factory recipe is the format-4 ROM map, and it strips the blob and blob-stream mailboxes that the older Coleco producers still declare.

## Unverified cells

These cells are deliberately not filled. The surrounding text is what the tree actually shows.

- **ZX80, TS1000, TS1500 — Quartus oracle.** Their recipes say `bring-up/check oracle`, and the only Quartus make target found for that shell is `build-fes-zx81-quartus`. Coverage of the other three models is unverified.
- **Every row with a pad or keyboard — Bluetooth.** Bluetooth HID/HoG pairing is a host evdev path in the FogCast README. No per-core Bluetooth interface was found.
- **Every row — Mesh / FogCast.** Launch, library and mesh are host services. No per-core mesh capability flag was found, so this page does not claim that any core is in or out of the mesh.
- **Registered recipes — Ship both builds.** No recipe records a completed OSS-versus-Quartus sign-off comparison against the 15% rule. i386 is the worked example of the gap and is Quartus-primary by policy; it is not a registered core. Which other current cores would qualify to ship a Quartus variant is unverified.
- **Catalog-supported and experimental rows — Current-byte kit acceptance.** Core status and the validation notes bind acceptance to named packages. This matrix does not copy those package ids forward. Which rows Deano wants marked HIL-verified for the bytes in the tree is open.
