# Native programming dispatch boundary

The [format-15 inventory stop](../2026-11-14-de25-rearm-inventory-stop/README.md) exposed an early host marker: the native session marked execution before entering the JTAG inventory gate. The actual inventory failed before any native program call. The consumed procedure correctly remained conservative and still requires the requested physical reset before restoration. This change does not reinterpret that attempt or change its frozen sources.

The new portable `NativeProgramDispatch` wrapper runs around the existing synchronous, one-use `ProgramAttempt`. It writes the durable execution marker inside the admitted programmer callback, after the existing inventory/forced scan and identity checks, and before the actual programmer callback can run. It does not perform a scan, choose an image, open a device, retry an attempt or grant recovery authority.

A live, completed, still-owned operation can report that programming was never invoked when its inventory gate rejected the image before dispatch. An incomplete or missing worker, lost ownership (including after a later successful guard), callback entry, existing/inaccessible marker or partial persistence stays uncertain. The dispatch marker precedes the programmer, and a consumed attempt cannot be reused. Success without a completed callback, a swallowed programmer error or a duplicate dispatch is rejected.

Twenty-two focused tests pass with zero skips using the actual one-use admission and the controlled scan producer. Four model tests run copies of the actual transport, native session, worker wiring and recovery-failure hooks with injected JTAG/programming/ownership/UART operations. They cover successful scan-to-dispatch ordering, the actual inventory error before native programming, an exception after dispatch, an early unclassified failure a missing worker, and propagation through the actual worker into the parent failure hook. The modeled inventory error permits only the existing pre-execution recovery classification; uncertainty continues to reject recovery. No physical kit is used, no existing failed trial is retried, and the current restoration remains gated on actual human reset confirmation.

The public helper and portable tests are in the common codebase. The prototype adapter copies and original source hashes are retained separately; adoption needs a newly frozen source-bound operator and its normal file/transport checks. This software milestone does not qualify native boot, source rearm, core loading, interconnect drain or general appliance acceptance. The original baseline file-admission check and seven restoration-only scope tests separately pass; actual physical reset confirmation and restoration execution remain pending.
