## Sender race and implementation

The [instrumented failed probe](diagnosed-race.json) identified the exact host
race: G-Kermit exited with status zero after all receiver acknowledgements,
while the host had sent 1,356 of 1,358 generated bytes and still held the final
CR/LF. The old loop stopped before its stdout/UART queues finished. It exhausted
the old implementation's two-failure limit and was not replayed. A separate
bounded JTAG cleanup restored its verified recovery prompt; there was no SD
write or native attempt in that failed diagnostic.

`uart_transfer.send` now drains stdout to EOF and sends all queued bytes after
a successful sender exit, retaining the same claim, time and RAM-wire bounds.
Nonzero exit, claim loss or an exceeded bound stops immediately. Status and
packet files remain available on failure. The [paired actual-loop replay](paired-relay-model.json)
reproduces the old two-byte failure and completes all 1,358 bytes with the fix.
Seven regressions cover queued output, unread stdout, failure, ownership,
wire bounds and deadline. The real sender and pinned C receiver pass six
1 MiB success/failure cases under each privilege level. Packet fixtures use
lossless hex because the repository's diff checker expects UTF-8; the initial
check failure and exact original bytes remain retained.

The [physical 1 KiB probe](ram-hardware-evidence.json) then passes 1,358/1,358
transmitted bytes, the firmware RAM hash, live LMB/session ownership and the
current return prompt. The read-only controller cannot issue an SD write,
network operation or native activation. This independently checked result is a
required, source-bound gate for the following recovery upgrade.
