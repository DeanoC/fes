# PC/386 diagnostic CMP reference experiment, 2026-11-16

This is an unfinished, default-off 286-reference diagnostic. It does not fix #1902, qualify a core or artifact, establish physical 286 timing, or close the speaker-pitch or tier-1 gates. The model is calibrated to 86Box v6 behavior; the RTL is an independent implementation and does not copy the GPL reference implementation.

The candidate changes the unprefixed 16-bit, single-byte opcodes 38/39 with a memory operand and instruction-wide ordinary-RAM access: execution budget 5 clocks, independent queue refill budget 7. Other prefixes, 386 encodings, register forms, reverse-direction 3A/3B, and non-RAM accesses retain the *previous diagnostic* path. The previous diagnostic already suppresses some baseline wait charges; this is not a claim of production timing or device conformance. The candidate gates on the accumulated instruction-wide ordinary-RAM predicate. Tests exercise it synthetically at the governor interface; they do not establish the actual whole-CPU RAM/MMIO boundary classification, word crossings, abandonment or replay for this change. The broad eligible predicate also includes base+index+displacement (EA3) and direct memory-destination forms that were not measured in this survey. Those forms are extrapolations, not individually qualified cases.

## Reference and controls

The prospective 20-case test in `inputs/` compares byte-identical timed loops and records isolated opcode bytes and positions in `instruction-identity.json`. It covers byte and word memory-destination 38/39, reverse-direction 3A/3B, indirect/indexed/displaced addressing, equal and unequal operands, and two loop scaffolds. Flags, both RAM words, registers, canary, stack and segment controls are checked. `PUSHF`/`POP` and scaffolding are part of each timed loop. The explicitly excluded DS- and ES-prefixed memory-destination cases remain about **1.992 clocks per whole loop too high**; they were not changed. Unprefixed 38/39 case estimates agree within 0.023 clocks per loop with the frozen candidate. Reverse-direction controls agree within 0.021 clocks. See `predictions/comparison-primary.json` and all three original `reference/CM*.TXT` files.

Three consecutive reference outputs are identical, SHA-256 `6a26d7ed22dc8c68a8a1beef92ccdce019c7b142a1199602eb03778534ebe116`. One isolated 86Box v6.0 boot used Award 286, 12.5 MHz, wait-state setting 1, and 1 MiB RAM; the reference executable SHA-256 is `ae3dc231824cf0c2facd1af4e2164814cbbb15bb1a9fa0603cdd8e9ee0ad2969`. The frozen reference manifest records emulator/ROM tree hashes, settings and private guest input hashes; it does not include ROM or disk contents. The full retained private 4 fps recording yielded 1,140/1,140 samples matching the visually verified 100% speed indicator (`reference/speed-audit-dual-template.json`). This sampled check says nothing about speed between samples. Each count represents 1,000-iteration blocks over 64 BIOS ticks; the reference estimate is `64 * 65536 * 12500000 / (1193182 * count * 1000)` clocks per loop. Tick quantization, timer/ISR and block setup, and differences between DOS and RTL marker overhead add uncertainty. Identical results in one boot are not independent boots or broad workload qualification.

`synthetic-frame/` retains a separate matched test that constructs a return frame and executes the same full or reduced handler without real interrupt/exception delivery. Full handler P0 reference/old diagnostic/new candidate is 223.047/231.172/227.170 clocks per whole loop; P8 is 238.806/247.172/243.170. The two opcode-38 instructions plausibly explain the observed four-clock improvement, while roughly 4–5 clocks remain in the full synthetic handler/frame/return group, subject to the same whole-loop limitations. The previous candidate's real #DE and software INT entry estimates remain inaccurate. No general fault or interrupt entry fix is claimed. The full/reduced synthetic control's three raw reference files are identical, with 620/620 4 fps samples at 100%.
