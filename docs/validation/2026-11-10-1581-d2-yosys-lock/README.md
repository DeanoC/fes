# #1581 D2: the i386 lock's Yosys moves to 0a7927bf

Decision D2 of [`docs/design/rtl-frontend-lanes.md`](../../design/rtl-frontend-lanes.md)
says one Yosys reads the i386 CPU. Before this change the i386 lock
(`sources/misteross/cores/fes-common/rtl/i386/toolchain.lock`) pinned DeanoC/yosys
`238eac9a49`, while the pc386 lock, whose Quartus producer seals the CPU, pinned
`0a7927bf`. This record shows that the move changes no netlist and no lockstep
result. The i386 lock now pins `0a7927bf126eb3d868c50b3bb5e11b69ff656ea9`. Its
other tools are unchanged.

## What the four extra commits could reach

`0a7927bf` is `238eac9a49` plus four commits:

| Commit | Change | Effect on the lockstep netlist |
| --- | --- | --- |
| #54 | `opt_merge` keeps replicated logic on `nomerge` wires | Can't apply: no file in `cores/fes-common/rtl/i386` or `cores/fes-pc386/rtl` has a `nomerge` attribute. |
| #57 | `proc_dlatch` carries `nomerge` through latch inference | Can't apply, for the same reason. |
| #60 | `wreduce` revisits readers when a shared Y is trimmed | Can't apply: the lockstep script (`read_verilog -sv; hierarchy; proc -norom; flatten; opt -purge; write_verilog -noattr`) runs no `wreduce`. |
| #68 | the hardware thread count is read once | Changes no output. |

## Runs

Every run is on tree `90bf76332` (main) with the old lock in place, except the
"new slot" row. All runs are host simulation only: no GPU, no kit. Verilator is
the i386 lock's v5.054 `bbb60a40` in every run.

| Run | Yosys | Binary sha256 | Slot |
| --- | --- | --- | --- |
| `lockstep-rtl`, `frontend-rtl` | none (RTL straight into Verilator) | — | `44e245aa…` (Verilator) |
| `lockstep-238eac9a`, `frontend-238eac9a` | `238eac9a4`, the old i386 lock | `66de9163d4fa1dec…` | `44e245aa…` |
| `lockstep-0a7927bf`, `frontend-0a7927bf` | `0a7927bf1`, from the pc386 OFF slot | `b6cd1fd2f56e22e2…` | `9092d69c…` |
| `lockstep-slot`, `frontend-slot` | `0a7927bf1`, from the new i386 lock's own slot | `804e424c012d9486…` | `ddc23ba2…` |

The new slot is `ddc23ba25a44cf71e5cd8cf87da51a7c9cbd73b26826e25caa1453c082b632f5`,
built by `scripts/bootstrap.sh` with the environment `make toolchain-fes-i386` sets
(GPU router OFF). `FES_TOOLCHAIN_LOCKFILE` pointed at a scratch copy of the edited
lock, sha256 `07f8111b…`, which is byte-identical to the committed lock. The slot
key depends only on the lock's bytes, not its path. For the "new slot" row the edited lock was in the tree, so
`i386_verilator.py` authenticated that slot's Verilator itself (`verilator.slot` in
`reports/lockstep-slot.json`).

Slot builds aren't bit-reproducible. The three `0a7927bf` binaries on this host
all have different sha256s: the new slot `ddc23ba2…` and the pc386 slots
`9092d69c…` and `544f7f8c…`. So do the two `238eac9a` slots, `44e245aa…` and
`053d3998…`. So this record names the Yosys
commit and the slot, and it compares outputs, not binaries.

## Results

**Netlists.** `fes_i386_cpu.netlist.v` from all three Yosys runs is 3,021,421
bytes. Apart from line 1, the `/* Generated by Yosys … (git sha1 …) */` comment,
it is identical: `tail -n +2 | sha256sum` gives
`d1ac043f7e895f4b98c6622bab4fb094e3c61f06983a3e9ce2e7c75a6ac150b0` in each run.
The netlists aren't committed because of their size. `quartus_fes_i386.py` uses
the same netlist script, so the netlist Quartus fits for the CPU doesn't change
either.

**Lockstep.** Run `python3 compare_reports.py A.json B.json`. The script is S3's
copy, and it skips only the `verilator` and `yosys` fields. It gives
0 differences and all hash fields equal for every pair:

- `lockstep-rtl` vs `lockstep-238eac9a`
- `lockstep-rtl` vs `lockstep-0a7927bf`
- `lockstep-238eac9a` vs `lockstep-0a7927bf`
- `lockstep-rtl` vs `lockstep-slot`

The trace hashes compared are:

- the seven case-mode hashes (`reset_store`, `directed_cases`, `unreal_cases`,
  `pmode_cases`, `paging_cases`, `no387_cases` and `memory_cases`);
- 941 corpus hashes;
- 16 random-seed hashes and 16 protected-mode hashes.

`random/trace_hash_mismatches` is empty in all four reports.

All four reports show the same single failure: `random#2#449` (31,999 of 32,000
random programs pass). That failure is #1425, a known lockstep harness issue already recorded in #1651.
A REP STOSD with DF set stores over its own encoding while an INTR is injected.
The RTL runs the whole REP, as a 386 would, but Bochs stops after the first
element because of how it handles self-modifying code. The RTL run hits it too,
so it doesn't depend on Yosys.

**Front end.** `test_fes_i386_frontend.py --yosys` gives identical reports for
`238eac9a`, `0a7927bf` and the new slot. That covers the lendec, front-end and DAG
records, plus the `qalign_synthesis` cell counts, which run `synth_intel_alm` and
so do run `wreduce`. Compared with the RTL run, the netlist runs differ in two ways. They add the
`qalign_synthesis` section, which only `--yosys` runs produce, and they report
`l2_empty_releases` as 0. That's by design:
`cores/fes-common/sim/i386/frontend_tb_top.sv:48` ties the probe to 0 in netlist
builds, because the hierarchy it reads is flattened away. The difference is the
same under both pins.

## What else this change touches

- **BUILD_ID.** No package producer reads the i386 lock, so no core's BUILD_ID
  moves. The pc386 Quartus producer pins the i386 `.sv` files and its own lock,
  not this one.
- **pc386 lock.** `cores/fes-pc386/toolchain.lock` is untouched. Any byte change
  to it moves the fes.pc386 BUILD_ID. Its stale rationale text and its Verilator
  move to v5.054 are #1660.
- **Each host.** The i386 OFF slot must be rebuilt
  (`make toolchain-fes-i386 CACHE_ROOT=…`, about 15 minutes on Powerboat), because
  the slot key hashes the lock. The i386 lock still has no HIP slot.
  `benchmark_fes_i386.py` and `synth_fes_pc386.py` need one, as before; nextpnr
  i386 routes are parked (#1235).
