# DE25 pc386 486SX: how fast it clocks (method, committed before any fit)

Deano, 24 Nov 2026: "lets have a session see what 486sx on de25 can clock to".
The standard DE25 pc386 on main is a 486SX (`I486 = 1`) with no 387 (#2171,
`4d08a0eac`), at a machine clock of 61.437908 MHz. This is a measurement
study, Refs #2135 (the DX plan, whose decision 4 asks for a PLL check of a 2×
integer core). No RTL changes and the registered producer's shipped clock does
not change: every clock other than 61.437908 MHz exists only on an unmerged
rung branch.

This file is committed and pushed before any fit in it is queued. A later
amendment is dated and says what had been seen by then. No rung, seed or rule
changes after a fit's output exists.

## What had been seen before this method

- #2171's four fits (`docs/validation/2026-11-23-de25-486sx`, design
  `4da642f9…` at `d1616104c`, not main's design) close at 61.437908 MHz with
  worst setup +1.247 ns. That worst setup, and every seed's, is a
  machine↔pixel held bundle bounded by `set_max_delay 10.000`
  (`pc386-clocks.sdc`); it does not scale with the machine period, so it is
  not a frequency headroom figure.
- The same fits' Fmax Summary gives the machine clock's same-clock Fmax as
  91.99, 94.31, 85.63 and 86.60 MHz (seeds 1–4), from a fitter that was asked
  for 61.44 MHz.
- x87 slice 6.0 (`2026-11-20-i386-x87-s6-measure`) closed `pc386_system`
  *with* the 387, in `fit_i386_device.py`'s virtual-pin envelope, at
  120 MHz on four seeds.
- The machine PLL (fit report of #2171's seed 2) runs its VCO at
  50 MHz × 188 / 3 = 3,133.333 MHz, with C = 51 for the machine and C = 255
  for the 12.287582 MHz audio master.
- Every machine↔audio-master path in that fit's top ten is the PCM bundle
  under `set_max_delay 10.000`.

## Q4 first: which machine clocks are legal

Derived, not measured. The audio master must stay at 12.287582 MHz (the I2S
runs at it / 256, 48 kHz at −34 ppm), so the PLL keeps M = 188, N = 3 and
C1 = 255, and the machine is VCO / C0 for an integer C0. Nothing else fixes
the machine clock:

- **Audio.** `pc386_system`'s AUDIO N/D is the audio master / 256 over the
  machine clock, (VCO / 255 / 256) / (VCO / C0) = **C0 / 65280**: 1/1280 at
  C0 = 51, the "machine / 1280" in `build.py`. Any C0 gives an exact ratio.
  The machine↔audio crossings are bounded by absolute `set_max_delay` /
  `set_false_path` constraints, not by the edge relationship of the two
  outputs, so a ratio that is not an integer is a timing problem only if a
  path between them is not one of the named crossings. Each rung's report is
  checked for that (below).
- **Guest rates.** Every other N/D is the guest rate over the exact machine
  clock `Fraction(9.4e9, 3 C0)`. For every rung below, each numerator and
  denominator is under 2^31 (largest 18,359,375), and the VGA dot clocks
  (28.322 MHz the highest) stay under the machine clock.
- **Video and the window.** The scanout pixel clock (74.25 MHz) and the
  peripheral clock (100 MHz) come from other PLLs; the machine reaches them
  only through the named crossings and the `fes_win_cdc` bridge. No ratio to
  either is required.
- **A 2× CPU clock.** C0 = 25.5 does not exist, so 2 × 61.437908 =
  122.876 MHz is not on this VCO. The 2:1 pairs on it are C0 = 50 with 25
  (62.667 / 125.333 MHz) and C0 = 52 with 26 (60.256 / 120.513 MHz).

## Q1: the board ladder

**What changes.** [`make_rung.py`](make_rung.py) `TREE C0` edits two files
of `sources/misteross/boards/de25nano/pc386/` and nothing else:

- `build.py`: `MACHINE_HZ`, `CLOCK`, `PLL_PARAMETERS`' output 0 and AUDIO's
  ratio (C0 / 65280). The guest rates and `ATA_RESET_CLOCKS` follow `CLOCK`
  unedited. `PLL_COMMENT`, a comment written into the board top, is left as
  it is, so it still says "/51".
- `machine_pll.ip`: `gui_output_clock_frequency0`. The IP's stale fields
  (output 0's `clockRate`, the `gui_*` VCO defaults) are left as they are.
  The PLL is regenerated by the board build from the IP as on main.

At C0 = 51 it computes the shipped values and edits nothing. Each rung is one
commit on a branch `deano/de25-486sx-fmax-cNN`, made by `make_rung.py` on
this method's commit and pushed before it is fitted; the record gives each
rung commit and its diff's digest. These branches are scratch and never
merge. The netlist differs at every rung (its guest-rate parameters do), so
each rung's netlist SHA-256 is recorded, and seeds 2–4 must have seed 1's.

**The rungs.**

| ---: | ---: | ---: |
| control | 51 | 61.437908 (this method's commit itself, no rung branch) |

The control is main's design at the shipped clock through this method's
path. Main's design has never been fitted (#2171's fits are `d1616104c`'s),
so the control is reported as its own result and is not a rung.

**How each fit runs.** [`fitrung.sh`](fitrung.sh) `REV SEED…` on Powerboat,
Quartus Pro 26.3, from a clean detached worktree of the pushed commit under
`/data/projects/fes-486sx-fmax`, with the pc386 lock's Yosys and
`YOSYS_MAX_THREADS=1`, as #2171's fits ran:

- **Seed 1** is the registered producer, `build_pc386_package.py`, unchanged.
  Its exit status and log are kept whatever they are.
- **Seeds 2–4** are copies of seed 1's generated project with only `SEED`
  changed in `golden_top.qsf`, compiled with `quartus_sh --flow compile`.
- Every Quartus program, the path reports included, runs under a Pro slot of
  the Quartus lease (`quartus_jobs.py run`, cap 300 minutes). A fit that hits
  the cap is **not measured** and counts as a miss for the ladder.

**The pass rule, per seed.** The fit completes; ALMs needed ≤ 46,800; and
every row of the timing analyser's summary (setup, hold, recovery, removal,
minimum pulse width, max skew, net delay, setup data delay: every clock or
target, every corner) has slack ≥ 0. Nothing else is a pass.

**The producer's verdict** is recorded beside the pass rule for seed 1 of
every rung: admitted, or refused with its reason. A refusal on signoff
findings is recorded with every rule ID and finding it names, because those
say what breaks. No signoff basis is added or changed and no check is
relaxed. A rung whose seed 1 passes the pass rule but is refused by the
producer is reported as "closes, not admitted".

**The ladder rule** (x87 slice 6.0's, unchanged):

1. Seed 1 runs at every rung, whatever the lower rungs show.
2. Take the highest rung R at which seed 1 passes and every lower rung's
   seed 1 also passed. Seeds 2–4 run at R. If all three pass, the full DE25
   486SX machine **closes at R on four seeds**.
3. If any of them misses, seeds 2–4 run once at the next lower rung, and the
   claim is that rung if all three pass there. The ladder then stops: no
   further rung or seed is added.
4. A seed 1 pass above a missing rung is reported, and is not a closure.
5. If no rung's seed 1 passes, the answer is "no rung above 61.437908 MHz".

## Q2: what limits a failing rung

For every fitted seed, [`paths.tcl`](paths.tcl) runs `quartus_sta` on the
kept project (under the lease) and writes, per corner: the 20,000 worst
machine-clock-to-machine-clock setup paths, one per endpoint; the 2,000 worst
setup paths each way between the machine clock and every other clock; and
every negative-slack setup, hold, recovery and removal path. From those the
record gives, for each failing rung:

- the worst paths by clock pair and analysis, and **period-scaled** against
  **fixed-bound** separately. A path is fixed-bound when its setup
  relationship is a `set_max_delay`, `set_data_delay`, `set_max_skew` or
  `set_net_delay` bound rather than a clock edge relationship. Fixed bounds do
  not move with the machine clock and are reported apart at every rung;
- every failing machine-clock path's endpoints by owner: **CPU**
  (`system|cpu_*`), **machine** (`system|machine_*`, `system|pixel_*`,
  `system|frame_*`), **anonymous** (`system|_N_`, Yosys auto-names, owner not
  attributable), and **shell** (anything outside `system|`: the window
  adapter and control block, the arbiter, `fes_win_cdc`, the scanout
  endpoint, audio). The pairs are counted as CPU→CPU, CPU→other, other→CPU
  and other→other;
- whether any machine↔audio-master path that is not one of the named
  crossings appears (a ratio failure, separate from logic depth);
- the machine clock's same-clock Fmax from the Fmax Summary, labelled as the
  analyser's estimate, not a closure.

The answer to "is the limit the CPU or the shell" is read from that count at
the lowest failing rung and is stated with its numbers.

## Q3: a CPU on its own faster clock

Answered from timing evidence; no clock-crossing design is built.

**The paths that would cross.** From every board seed's machine-setup report:
the paths with exactly one end in `system|cpu_*`. Their count, and the
distribution of data delay plus clock skew, against the 7.979 ns period of
the C0 = 25 CPU clock in the 62.667 / 125.333 MHz pair. With both clocks from
one PLL at 2:1, an unannotated path between them gets one fast period, so a
boundary path longer than that needs a registered boundary or a multicycle
that the RTL guarantees. The record names which and how many; it does not
build either.

**Envelope fits** on chip-30x0-ai-dev, Quartus Pro 26.3, with
`scripts/fit_i386_device.py` unmodified, from a clean checkout of this
method's commit with [`envelope-i486.patch`](envelope-i486.patch) applied.
The patch sets the `I486` default to 1 in `fes_i386_cpu` and in
`pc386_system`, because the runner passes no `I486`. It is a scratch edit and
not RTL that merges. Each fit's netlist is checked for the 486SX
(`eflags` 22 bits wide). Each fit holds the lease through the runner's own
`compiler_lease`.

- `--design cpu`, `fes_i386_cpu` alone, every port a virtual pin with its
  paths cut: the CPU's own register-to-register paths.
- `--design machine`, `pc386_system` with the DE10 guest rates, the same
  envelope: the CPU together with its real boundary into the machine's
  memory, I/O and devices, all at the one clock.

Each runs at `--period-ns 7.979` (125.333 MHz), seeds 1–4. A design passes
when the runner's timing gate passes on all four seeds. If any seed misses,
that design runs seeds 1–4 at `--period-ns 8.298` (120.513 MHz) and stops.
What neither fit has is the shell: the window adapter, the arbiter and the
bridge stay at the machine clock in a 2× design, so the board ladder, not the
envelope, says whether the shell is the limit.

## Recommendation

The record ends with one recommendation for the next speed step: a raised
single machine clock (naming the rung), a separate CPU clock (naming the
boundary work), or a specific RTL fix (naming the paths). It is a
recommendation for Deano, not a change.
