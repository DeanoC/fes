# PC/XT Digger readiness study

This study is an offline aid for designing a future game test. It does not
establish that the game is playable on the kit, authorize a kit run or change
the existing game diagnostic. The two retained captures are from the same
source lineage and are very similar; they cannot establish general detector
accuracy. The first is a recorded failed attempt and the second has an
inconclusive movement review. In particular, a pair of opening-screen matches
is not proof of a successful left/right/left sequence.

`scripts/pcxt_digger_readiness.py` contains an experimental fixed-coordinate
classifier and a one-shot freshness model. The classifier uses private,
externally supplied image crops, not bundled game assets. The model accepts
sequence numbers and timestamps as inputs; it cannot prove that a device
supplied them honestly or that they bound the age of a frame. Its explicit
thresholds are parameters for experiments, not qualified kit defaults.

For the retained private recordings, `scripts/pcxt_digger_replay.py` verifies
the full video hashes, re-derives and checks the crop hashes, and cross-replays
the first and second run at half-second sample intervals. An example with the
locally retained data is:

```sh
python3 -I -B scripts/pcxt_digger_replay.py \
  --first-video /path/to/first/game-full.mkv \
  --last-video /path/to/last/game-full.mkv
```

The replay uses FFmpeg at 2 fps on the 1920x1080 recordings, followed by
`scale=640:360:flags=neighbor`, RGB24, and crops of `32:34:304:322`,
`80:76:350:280` and `70:30:190:0` respectively. FFmpeg's offline `fps` filter
may duplicate frames, so this replay is **not** evidence of two fresh source
observations. It checks the derived crop hashes against the retained study and
deletes the temporary crops after reading them.

The study detects opening candidates at 43.5 and 44.0 seconds, rejects the
sampled known negative and respawn intervals, and detects the particular
approaching threat at 49–50 seconds. These are observations about those two
recordings only. A different screen geometry, animation, enemy, later restart,
frozen capture or other unseen scene could defeat the classifier.

Before using any such gate for live input, a new implementation needs a
continuously recorded capture stream with a separately drained bounded
observation path, source-frame sequencing and defensible capture-age bounds.
It must show recording integrity despite a stalled or failed observer and
must establish a credible observation-to-guest-input bound. Arrival time and
FFmpeg progress messages provide neither guarantee. Validate the actual branch
against realistic delayed, duplicate, frozen, malformed and dropped inputs;
retain the unchanged ownership and input guards; independently review the
algorithm and controls; and preserve the prior attempt history. Only then can
a new source-bound kit attempt be separately assessed. Gameplay, directional
response and speaker-audio conclusions require their own retained physical
evidence.

## Experimental acquisition path and calibration

The separate `pcxt_v4l2_capture.c` experiment emits the V4L2 buffer sequence,
V4L2 timestamp and its flags, monotonic dequeue time, and the original YUYV
frame from one device handle. `pcxt_capture_fanout.py` validates this stream,
records every frame through FFV1 with a timestamp sidecar, and sends selected
frames to an independently drained latest-only detector queue. A recorder
overrun or source discontinuity fails the experiment; a detector crash, stall
or dropped observation invalidates detector evidence without blocking the
recording. The recorder verifies the timestamp sidecar and re-decodes the FFV1
file to check each frame's raw hash. A bounded source-process wrapper rejects an
early exit and verifies a planned stop. The fixed playback frame rate is not an
input timestamp. These
components are experimental and are not connected to the live game diagnostic.

`scripts/pcxt_capture_replay.py` can send a short excerpt of a private 1080p
recording through the same wire parser, fanout and FFV1 verifier. It generates
synthetic sequence numbers and host delivery times, so it tests transport and
recording rather than source timestamps, real-time throughput, or gameplay.

The kernel timestamp is not an FPGA video-generation timestamp. A monotonic
flag establishes the timestamp's clock domain only; it does not bound camera,
HDMI capture, or other upstream buffering, and it does not prove that visually
identical frames were independently generated by the target. Consequently the
model's `max_age_ns` cannot be selected from the existing recording. A host
request timestamp also does not show when a USB input reached the guest.

Before using the path to trigger gameplay input, perform a separate, claimed-kit
calibration on a source-identified diagnostic package and retain its package,
host, capture device, build and tool identities:

1. Check the V4L2 mode, sequence, flags and timestamp behavior with the live
   driver; retain the unmodified frame sidecar and video. Characterize startup,
   resolution changes, induced delay, frame loss and disconnect/reconnect. Stop
   if timestamps are not monotonic or the source silently repeats frozen frames.
2. Generate a rapidly changing, uniquely numbered video pattern at the target,
   and use a hardware-timestamped reference or independently synchronized
   signal marking its change to measure the target-to-capture delay, including
   the capture device's buffering. Test the same mode, acquisition path and
   realistic host loads. A sequence observed only after capture cannot itself
   establish when the target generated it.
3. In a separate controlled input diagnostic, timestamp a physical or otherwise
   independently observed input event and its guest-visible effect, using an
   independent reference shared with the video measurement. Measure the full
   observation-to-guest path under the same load, including the unchanged
   ownership and input checks. Host API response times alone are not that bound.
4. Predeclare the operating envelope, uncertainty, required guard margin and
   the tests that invalidate it. Retain all traces and outliers. Measured
   samples characterize the tested setup; they are not an unconditional upper
   bound. If a defensible operating bound cannot be established, keep automatic
   live input disabled and use a separately reviewed manual or instrumented
   test design instead.
5. On the exact game build, verify the opening detector against independent
   positive and negative scenes, movement and respawn cases. Separately prove
   a neutral control and the predeclared left/right/left comparisons. Re-run the
   guard against the newest admissible frame immediately before each permitted
   operation, and stop on any stale, missing or uncertain observation or input.

No physical calibration, live game input, or hardware qualification has been
performed by this study.

The game diagnostic uses one source for both the retained FFV1 recording and
the opening-scene observer. It checks for a completed observation of the most
recent acquired frame after the normal ownership and input checks, records a
neutral interval, and issues the predeclared left/right/left sequence. The local
host-age policy rejects obviously stale observations; it is not a bound on the
age of the target image or on key delivery. The diagnostic requires an
explicitly hashed native capture helper and private opening-player templates.
It preserves per-frame source metadata and input requests and receipts.

The result is always **review pending**. A reviewer must inspect the video and
input trace independently and establish an active player, a neutral control,
and the ordered left/right/left responses. Ambiguous timing, a death, an
obscured player, continued autonomous motion, missing frames or an uncertain
input response makes the attempt inconclusive. The diagnostic does not capture
speaker audio and cannot establish audio/video synchronization. Historical
failed and inconclusive attempts remain part of the lineage.

The input transport does not enforce a deadline before delivery. The gameplay
probe does not claim that host timestamps establish when the guest saw a key.
