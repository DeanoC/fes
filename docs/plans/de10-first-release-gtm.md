# First DE10-Nano / MiSTer FES release: go-to-market plan

**Status:** proposed plan, 29 October 2026. **Board:** Terasic DE10-Nano with the Cyclone V target documented in the repository. **Release shape:** a flashable FES image, independently installed core packages, and a first-run experience that makes the supported path understandable without a development workstation.

This is a release plan, not an acceptance record. The default image currently contains the `fes.menu` display package and the locked idle/splash RBF; playable cores are installed separately. A library `supported` label describes catalog standing, not hardware acceptance of the current bytes. The scope below uses the fetched `docs/support-matrix.json` snapshot on [PR #1240](https://github.com/DeanoC/fes/pull/1240), head `47247f7` (still open when this plan was written), alongside the current [core status](../core-status.md), [default profile](../../profiles/native-integration-dev.toml), and [core recipes](../../config/core-recipes.toml).

## 1. Release scope

### Board and package tiers

Keep the base image small. It should boot the board, provide the FES menu/tenfoot surface, and let the owner install playable packages from the catalog. Do not turn every development recipe into a factory-image dependency.

| Repository tier | Key systems | Proposed v1 treatment |
| --- | --- | --- |
| Firmware | `fes.menu`; `splash` / idle | Required base image. The menu is display firmware, not a playable system; splash is board firmware, not a game. |
| **Tier 1 — Catalog supported** | `fes.pong`, `fes.ramtest`, `fes.zx81`, `fes.coleco`, `fes.sms`, `fes.sg1000` | Candidate supported catalog set, only after the per-package release gates below. Put Pong on the first-play path because it needs no user ROM. Put RAM Tester under Utilities. Make ZX81, SMS and SG-1000 first-release systems only after firmware/media setup and their exact hardware checks are simple to follow. Hold Coleco from the promoted set until its title/media path is repaired: the matrix snapshot says its older media handling currently shows zero titles. |
| **Tier 2 — Optional** | `fes.atari-st` | Optional/advanced catalog package, not a first-run promise. Its user journey includes firmware, writable floppy media, mouse/input and video-part choices. Promote after that complete path has its own HIL. |
| **Tier 3 — Experimental** | `fes.zx80`, `fes.ts1000`, `fes.ts1500`, `fes.apple2`, `fes.c64`, `fes.spectrum`, `fes.spectrum128`, `fes.spectrum-plus3`, `fes.pentagon`, `fes.riscv` | Show only in an explicitly marked Experimental section. Do not count these toward the supported-core headline or imply that evidence for one model accepts another. C64 and Spectrum have useful package and kit diagnostics; consult each model's current core-status row before describing any feature as accepted. |
| Demo | `fes.catch` | A separate small demo entry if its exact package passes the same launch/Stop checks. Do not describe its `demo` standing as supported. |
| Outside the play catalog | `fes.demo`, `sim.pong`, PC/XT and pc386 bring-up, shared CPU RTL | Keep these as development/reference material, not end-user systems. |

The matrix's Tier 1 means `standing = supported` in the core library with a recipe row. It does **not** mean that a release image or the current package has passed HIL. The [core status](../core-status.md) contains artifact-specific evidence and open limitations; use that as the final gate. The recommended launch set is intentionally narrower than the catalog: Pong plus a small, well-tested set of systems with a complete firmware/media flow. The exact set is an owner decision after the matrix lands and candidate artifacts are reviewed.

### What must land or be accepted first

1. **Merge and maintain the support inventory.** PR [#1240](https://github.com/DeanoC/fes/pull/1240) is open. Its matrix distinguishes package standing, optional recipes, firmware, hardware evidence and toolchain policy; use the merged `docs/support-matrix.json` as the inventory source for the final release page.
2. **Finish the current tenfoot navigation stack.** PR [#1182](https://github.com/DeanoC/fes/pull/1182) adds family workbenches and guided setup; [#1187](https://github.com/DeanoC/fes/pull/1187) is stacked on it and polishes names/navigation. Both are open. Merge in dependency order, then validate the resulting bundle on the release image. Their host-rendering and earlier-kit evidence does not accept their current heads on a new image.
3. **Build and accept one named DE10 release image.** The core catalog, menu firmware, target software bundle, boot image and host are separate artifacts. Record their exact commits and hashes. Run clean image/media verification, then boot and exercise that exact flashable image on a DE10-Nano. No current open PR in the observed list supplies this complete first-release image acceptance.
4. **Accept each promoted core on its exact package bytes.** Test video/audio, input, ROM or media load, Stop/return, and save behavior when the core advertises persistence. A previous package or image result does not roll forward. Leave non-accepted packages explicitly experimental.
5. **Label the actual toolchain.** The accepted policy in [Quartus-built cores](../design/quartus-cores.md) defines `oss` as the Debian-style open set (Yosys + nextpnr-mistral) and `quartus` as the proprietary/non-free set. Registered recipes and package selection currently build/select the OSS lane only; there is no automatic Quartus fallback and no current dual-toolchain package declaration. Until the product selector and package labels land, publish the launch set as **OSS-built**. If a future core qualifies for both variants under the policy, show the variant in the catalog and release manifest and keep both build identities distinct.
6. **Resolve host-config privacy before choosing a split-host quickstart.** PR [#1211](https://github.com/DeanoC/fes/pull/1211) fixes explicit-config catalog-store selection. If the release path asks users to run a host on a PC, merge and validate that path. Do not distribute an image provisioned with a shared development token.

The open DE25-Nano board/first-boot PRs in the current list target a different FPGA and do not block this DE10-Nano plan. PR [#1145](https://github.com/DeanoC/fes/pull/1145) matters only if Pentagon disk behavior is promoted from Experimental; otherwise it is outside the supported launch set.

### Release criteria

- **HIL:** a freshly flashed, identified DE10-Nano boots the exact release image to the expected FES screen, displays stable HDMI, accepts the documented wired and supported Bluetooth controllers, installs and runs each promoted package, loads the representative licensed/user-supplied firmware and media, returns cleanly from Stop, and preserves only the save data promised for that core. Check update and recovery behavior on the same named software/image combination. Record the image, bundle, package IDs/digests, source revisions, toolchain labels, controller models and results in dated validation evidence. Host tests, simulation, route timing, package seals and an older kit note are useful inputs but do not replace this exact-artifact HIL.
- **Image:** publish one reproducible, checksummed flashable image with a clean first boot and tested restore path. Keep the default profile closed around the menu/idle firmware; core packages remain separate downloads/selections. Verify the image and media receipts before HIL, then bind the HIL record to their hashes. Public first-run media must use per-device onboarding/configuration, not a developer's host token.
- **Toolchain labels:** show `OSS (Debian-style)` or `Quartus (non-free)` where a package is selected and in the release manifest. Never label a Quartus oracle/check as a shipped Quartus variant. Today, the expected label for registered products is OSS. Do not advertise both variants until the core's recipe, package identity, selector, and matched timing/seal gates implement the accepted policy.
- **Support wording:** publish a promoted-core list separately from Experimental, Demo, and Utilities. Each promoted system has exact-artifact checks for the media, firmware and controller features advertised. The matrix tier alone is not a support claim.

## 2. First-user flow, end to end

The user should be able to go from unopened DE10-Nano kit to a playable title without reading developer build instructions or editing TOML. The current foundations are useful but spread across developer-facing commands and different configuration surfaces.

| Stage | Current repository behavior | First-release experience |
| --- | --- | --- |
| **Flash and first boot** | [Bootable media](../bootable-media.md) explains building and verifying a raw image, private host provisioning, identities and card-side config. [Getting started](../getting-started.md) starts with a source checkout and developer toolchain. The default profile has MENU and idle firmware but no playable core. | Provide a versioned image download, checksum/signature, a short cross-platform flash guide, card-capacity warning and recovery instructions. On first boot, show one FES welcome screen, storage/network status, controller choice and a clear path to the Systems shelf. Use a device-local pairing/config step; never bake a shared credential into a public image. Explain that games/firmware are not bundled and why. |
| **Menu / tenfoot** | FogCast's tenfoot renderer and rooms share navigation, Details, launch readiness and return behavior ([tenfoot launcher](../../sources/FogCast/docs/native-tenfoot-launcher/README.md), [rooms experience](../../sources/FogCast/docs/rooms-experience.md)). The requested family workbench and name/navigation polish are still open in #1182/#1187. | Make Home, Systems, Library, Settings and Updates a consistent shallow route. Present systems by familiar model name, then family/model/edition where needed. Details must state what is installed, what is missing, which controller/media is needed and the primary action. Stop returns to the prior shelf and selection. Keep rooms as authored destinations, not competing copies of the catalog. |
| **ROM and media folders** | The minimal host example has no library roots. A host library is configured by absolute per-system roots and scanned with the `fogcast scan` CLI ([getting started](../getting-started.md), [FogCast config](../../sources/FogCast/fogcast/config.go)). Tenfoot can add roots, but currently asks for a path via its on-screen keyboard ([settings](../../sources/FogCast/ui/tenfoot/settings.go)); its separate Drive screen can browse USB/SMB storage and choose BIOS/media folders ([storage settings](../../sources/FogCast/ui/tenfoot/storage_settings.go)). The browser catalog page says scanning is an internal CLI command and only reads the catalog (`sources/FogCast/internal/hostapi/ui_app.js`); the tenfoot empty shelf says “No games in this library yet” (`sources/FogCast/ui/tenfoot/localcore.go`). The configured folder-watch default in `sources/FogCast/internal/systems/table.go` is `//deano-clawz/Games/Games`, a development-machine path, not a portable consumer default. | Offer one guided source choice: USB drive on the kit, a host folder, or a documented SMB/NAS share. Suggest a simple per-system folder layout without requiring it; allow a user to choose one root and map its system. Replace developer-specific defaults. Show scan progress, supported/unsupported counts, duplicate handling and rescan status. Empty, offline and inaccessible states should offer “Add a folder,” “Rescan,” and a ROM-less demo rather than a dead end. Keep files on the user's chosen storage and never copy firmware/ROMs into core packages. |
| **Controller setup and Bluetooth** | Kit software includes a BlueZ pairing agent. It discovers and auto-pairs identified gamepads from its controller policy (`platform/cmd/fes-bluetooth/main_linux.go`, `platform/internal/btagent/policy.go`, `image/buildroot/board/fogcast-target/native-rootfs-overlay/etc/init.d/S41fes-bluetooth`). Tenfoot maps physical input and has a GUID-keyed saved profile with a `swap-ab` preset and per-control bindings (`sources/FogCast/ui/inputmap/`, `sources/FogCast/ui/tenfoot/safearea.go`). The current on-kit setup does not present a pairing wizard or a profile editor. | Make wired setup the immediate fallback; explain how to put supported pads into pairing mode and show “searching / paired / reconnecting / unsupported” status. Give the user a button test page and explain positional A/B labels. Surface the supported Bluetooth models and dongle requirements established by HIL. Provide a **global per-controller profile** for menu and all games, plus **per-core gameplay overrides**. Show defaults, reset-to-default and precedence. Keep the system-menu action and keyboard recovery route available regardless of a game's mapping. |
| **Choose, launch, save/load** | The library and core catalog already model install state and readiness reasons such as Needs BIOS, Needs a cartridge, unavailable or in-use (`sources/FogCast/ui/tenfoot/library_detail.go`, `sources/FogCast/ui/tenfoot/core_library.go`). Core setup and selected media are package-specific ([core package library](../core-packages.md)). Persistence is capability-specific: Pong stores settings/best rally at successful Stop; writable Atari ST media has its own durable path; ZX81 BASIC SAVE storage/acknowledgement is still marked pending; there is no universal save-state promise ([core persistence](../core-persistence.md), [core status](../core-status.md)). | Let the user select a title, inspect requirements, install a compatible package, add required firmware/media, then Play. Show a clear loading result and return to the same title on Stop. Put Save/Load actions only where implemented. Explain the difference between in-game battery/disk persistence and emulator save states; do not display a generic Save State control for unsupported cores. Confirm save completion or offer a retry before leaving a session whose save failed. |
| **Updates** | The repository separates base OS/image, immutable kit-software bundles, independently selected core/media packages and host software ([modular updates](../modular-updates.md), [FogCast appliance updates](../../sources/FogCast/docs/appliance-updates.md)). Package selection can change for the next launch without service restart; base-image and kit-software activation have different reboot/maintenance boundaries. | Put “Update system,” “Update FES software,” and per-core updates behind one readable entry, but preserve their actual boundaries. Show download size, current/available versions, required restart, compatibility and rollback/recovery action before confirmation. Keep core updates independent from image updates and never silently switch a currently running package. |

## 3. Visual polish

The repo already has a visual language, native renderer captures and a shared controller contract ([UX overview](../ux/README.md), [visual language](../ux/visual-language.md), [controller bindings](../../sources/FogCast/docs/rooms-controller-bindings.md)). Use that work to make one coherent product:

- **System identity and naming:** use “Sinclair ZX81,” “ColecoVision,” “Sega Master System,” and “Commodore 64” in user-facing shelves. Keep recipe IDs, package hashes, build names and diagnostic suffixes in Details or developer diagnostics. The plain-name work is part of open #1187.
- **Icons and artwork:** commission or create one original system icon per promoted model/family, with shared size, silhouette and contrast rules. Use game cover art only when supplied or legally usable. If no cover exists, keep the same card geometry and show the complete title, creator when known, and an identified system motif; never fabricate compatibility or ship unlicensed box art/ROMs. Show keyboard, controller, disk and firmware requirements as consistent readable marks.
- **Rooms and navigation:** keep Home → Systems/Library/Rooms/Settings consistent across keyboard, pointer and gamepad. Use one selected-item hierarchy and one meaning for Confirm, Details, Back and the system menu. Remove duplicate legacy rooms as the replacement system shelves land. Check 1280×720 and 1024×600, safe areas, long names and large text.
- **Readiness, error and empty states:** use labels and explanations, not color alone. Give loading, no media, missing firmware, unsupported format, offline host, disconnected controller, failed update and failed save distinct copy and an actionable next step. Preserve focus and selection when asynchronous metadata/art arrives. Show a useful empty-library action and a ROM-less first-play option.

## 4. Gap analysis and proposed work order

Sizing is a planning estimate, not a commitment: **S** is a few focused days, **M** roughly one to two person-weeks, and **L** roughly two to four person-weeks. Assumption: one engineer can own a slice at a time, with separate UI, image and hardware work coordinated. HIL time and review can extend any estimate.

| Order | Proposed issue / epic | Size | Concrete exit condition |
| --- | --- | --- | --- |
| 1 | **Publish and freeze the DE10 support matrix** (land #1240) | S | The maintained matrix is on main, distinguishes catalog standing from exact-artifact acceptance, lists the selected v1 systems and does not inherit DE25 results. |
| 2 | **Finish tenfoot model/family setup and navigation** (land #1182, then #1187) | M | The dependency stack is merged; supported families and variants have one understandable setup route; names are consistent; validate the current bundle on the release image. |
| 3 | **Create the consumer image and first-boot path** | M | Downloadable, checksummed image; safe per-device configuration; clean first boot; network/storage/controller status; recovery path; no development credential or machine-specific default. |
| 4 | **Replace path-entry library setup with a guided media wizard** | L | Select USB/host/SMB root; map systems; show a documented folder default; scan/rescan in UI with progress and clear unsupported-file reports; no games, offline and permission errors each have a next action. |
| 5 | **Add controller onboarding and global/per-core mapping UI** | L | Supported wired and Bluetooth pads pass the release HIL; pairing status and recovery instructions are visible; a global pad profile and per-core gameplay override can be changed/reset from the UI; precedence, labels and default mappings are tested; the system-menu action stays non-remappable and keyboard recovery works. |
| 6 | **Close launch, firmware and save promises for promoted cores** | M–L | Each promoted title has a verified ready-state path, exact firmware/media requirements, input/video/audio test, Stop-to-shelf test and accurately exposed persistence. Fix Coleco's zero-title path before promoting it; finish ZX81 save storage or do not advertise SAVE persistence. |
| 7 | **Unify updates, version labels and recovery copy** | M | The UI distinguishes image, kit-software, host and core/package updates; clearly shows OSS vs Quartus provenance where relevant; update, restart and rollback are tested on the exact release artifacts. |
| 8 | **Complete catalog artwork, contrast and empty/error-state pass** | M | Original system art for promoted systems; legal cover-art policy; naming/navigation consistency; selected/blocked/empty/loading/error states reviewed at target resolutions and with sparse controllers. |
| 9 | **Write the public quickstart and release landing page** | M | A non-developer can flash, first-boot, pair a controller, install a core, add their own ROM/media, launch/stop and update by following the page. Include legal-media guidance, checksums, known gaps and support channels. |
| 10 | **Run a release-candidate acceptance cycle** | M plus kit availability | Fresh image and selected packages pass the complete checklist below; publish the hashes and exact evidence. Any failed gate moves the date or removes that package from the supported list. |

Current open PRs are inputs, not completed release gates. #1182/#1187 report useful host/render and earlier-kit results but explicitly leave current-bundle kit acceptance open. #1211 should be resolved if the documented separate-host workflow is used. DE25 work in #1176, #1201, #1213 and #1238 should stay out of the DE10 release checklist. The UX acceptance plan and [core status](../core-status.md) should remain the evidence sources rather than this planning document becoming a second status tracker.

## 5. Go-to-market

### Target users

**Assumption:** the first audience is technically confident DE10-Nano owners: existing MiSTer users interested in a small set of original/open cores, FPGA hobbyists who value an open Yosys/nextpnr route, and retro-computing/homebrew users who are comfortable supplying their own firmware and game media. Do not target plug-and-play console buyers until the folder, controller and update paths work without shell commands.

### Positioning against stock MiSTer

Position FES as a focused, open DE10-Nano FPGA platform with a package-based core catalog, a navigable tenfoot/room interface and an OSS build lane for its supported Cyclone V recipes. The project README itself notes that FES supports fewer systems than MiSTer and emphasizes its expansion/cartridge bus model and OSS toolchain. Do not claim MiSTer compatibility, equivalent breadth, drop-in core coverage, or universally open toolchains. Distinguish FES packages from stock MiSTer RBFs and say plainly which systems require user-supplied ROMs/firmware.

### Docs, website and quickstart

Keep developer build instructions in the existing [getting-started](../getting-started.md), [bootable-media](../bootable-media.md) and [development](../development.md) pages. Add an end-user quickstart linked from the README and a small release landing page with: supported board and image version; flash/checksum steps; first boot; controller and Bluetooth support; library folder layout; core install; legal firmware/ROM guidance; update/recovery; exact supported/experimental list; and troubleshooting. **Assumption:** the website host and owner are not specified in this repository; use the project-controlled public site if one exists, otherwise publish the initial landing page with the GitHub release/docs and keep it versioned here.

### Community channels

Use the GitHub release and Discussions/issues as the canonical download, changelog and support record. **Assumption:** announce a short demo and the same quickstart in the MiSTer community forum/Discord and retro-computing/homebrew communities, following each community's promotion rules. Ask for a bounded beta cohort focused on clean install, controller pairing, first game, media setup and update/rollback; collect reproducible reports with image/core version, not private ROMs or credentials.

### Release checklist

- Freeze the v1 catalog list and mark each system Supported, Experimental, Demo or Utility with its required ROM/firmware/media and its actual toolchain label.
- Build the named flashable image and kit-software bundle from reviewed source; capture hashes, reproducibility/verification receipts, package IDs and licenses/provenance.
- Confirm the public image has no developer config, token, ROM, firmware or unlicensed artwork. Provide checksums and a recovery image/path.
- Complete exact-image DE10 HIL: cold boot, HDMI, menu focus, wired and Bluetooth controller, library scan, install, launch, media, audio/input/video, Stop, save failure/retry where supported, system update, core update, rollback and reboot.
- Test a clean user profile with no preconfigured library and no network. Confirm the empty screen remains useful; after installing a ROM-less package such as Pong, confirm it still launches offline.
- Publish the quickstart, known limitations, update compatibility table, toolchain labels, supported-controller list and contact/support location.
- Tag the source and release artifacts together. Keep the observed hardware evidence class and its scope explicit; do not turn package, simulation or aggregate timing results into a release-image acceptance claim.

### Suggested timeline

**Assumption:** a six-week sequence after the support-matrix and tenfoot PRs are mergeable, with access to a DE10 test kit and a small number of contributors. This is gate-based; do not preserve dates by weakening criteria.

| Window | Milestone |
| --- | --- |
| Week 0 | Freeze supported vs experimental list; land #1240 and the #1182 → #1187 UI stack; settle the OSS/Quartus presentation and no-ROM distribution policy. |
| Weeks 1–2 | Finish first-boot configuration, library/media wizard, controller setup and the public quickstart. Select the first exact core packages and close their user-flow blockers. |
| Weeks 3–4 | Produce the release image and package set; run clean-host checks, then exact-image HIL for install, first play, saves, update and recovery. Fix failures and rerun only affected evidence on final artifacts. |
| Week 5 | Publish a limited beta with the known-issues list; gather first-user results and resolve only release-blocking issues. Rebuild/retest any changed image or package. |
| Week 6 | Tag and publish GA if every release criterion passes; otherwise continue beta and move the date. Publish hashes, supported matrix, quickstart and rollback instructions together. |

## Assumptions and scope boundaries

- The first public target is DE10-Nano/Cyclone V; DE25-Nano/Agilex 5 is a separate product and Quartus Pro path.
- FES distributes no proprietary game ROMs or firmware. The owner supplies any required content unless a separate distribution license is documented.
- v1 uses the existing modular image/core architecture; this plan does not move playable cores into the default OS image.
- Website ownership, beta size, contributor availability and exact release date are not recorded in the repository. Timeline and channel recommendations above are assumptions.
- HIL claims apply only to the recorded image, software bundle, package and tested features. A later artifact needs its own acceptance.
