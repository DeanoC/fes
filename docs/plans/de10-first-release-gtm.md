# First DE10-Nano / MiSTer FES release: go-to-market plan

**Status:** proposed plan, 29 October 2026. **Board:** Terasic DE10-Nano with the Cyclone V target documented in the repository. **Release shape:** a flashable FES image, independently installed core packages, and a first-run experience that makes the supported path understandable without a development workstation.

This is a release plan, not an acceptance record. The default image currently contains the `fes.menu` display package and the locked idle/splash RBF; playable cores are installed separately. A library `supported` label describes catalog standing, not hardware acceptance of the current bytes. The working scope below is re-derived from per-core Git history, dated kit records, and concrete model/package variants. The maintained [core support matrix](../support-matrix.md) is the inventory reference; this remains a product proposal, not a matrix tier or acceptance claim.


**First boot and setup:** the v1 decisions (four families, Home, folders, firmware, controllers) and milestone issues are in [v1 first-release first-boot & setup plan](v1-first-release-first-boot-setup.md).

### What must land or be accepted first

1. **Align product scope with the maintained support inventory.** The [core support matrix](../support-matrix.md) is on main. Reconcile package names, variants and catalog standing with it, while keeping tier, product scope and exact-artifact HIL as separate decisions. Use the matrix as the inventory source, not as a substitute for product scope or hardware acceptance.
2. **Finish the current tenfoot navigation stack.** PR [#1182](https://github.com/DeanoC/fes/pull/1182) adds family workbenches and guided setup; [#1187](https://github.com/DeanoC/fes/pull/1187) is stacked on it and polishes names/navigation. Both are open. Merge in dependency order, then validate the resulting bundle on the release image. Their host-rendering and earlier-kit evidence does not accept their current heads on a new image.
3. **Build and accept one named DE10 release image.** The core catalog, menu firmware, target software bundle, boot image and host are separate artifacts. Record their exact commits and hashes. Run clean image/media verification, then boot and exercise that exact flashable image on a DE10-Nano. The current repository has no record of this complete first-release image acceptance.
4. **Accept each promoted core on its exact package bytes.** Test video/audio, input, ROM or media load, Stop/return, and save behavior when the core advertises persistence. A previous package or image result does not roll forward. Leave non-accepted packages explicitly experimental.
5. **Label the actual toolchain.** The accepted policy in [Quartus-built cores](../design/quartus-cores.md) defines `oss` as the Debian-style open set (Yosys + nextpnr-mistral) and `quartus` as the proprietary/non-free set. Registered recipes and package selection currently build/select the OSS lane only; there is no automatic Quartus fallback and no current dual-toolchain package declaration. Until the product selector and package labels land, publish the launch set as **OSS-built**. If a future core qualifies for both variants under the policy, show the variant in the catalog and release manifest and keep both build identities distinct.
6. **Resolve host-config privacy before choosing a split-host quickstart.** PR [#1211](https://github.com/DeanoC/fes/pull/1211) fixes explicit-config catalog-store selection. If the release path asks users to run a host on a PC, merge and validate that path. Do not distribute an image provisioned with a shared development token.

DE25-Nano PRs [#1176](https://github.com/DeanoC/fes/pull/1176) (board and FPGA/HPS diagnostics), [#1201](https://github.com/DeanoC/fes/pull/1201) (idle/menu scanout), [#1179](https://github.com/DeanoC/fes/pull/1179) (headless Linux checks) and [#1238](https://github.com/DeanoC/fes/pull/1238) (read-only first-boot evidence preparation) are merged; [#1213](https://github.com/DeanoC/fes/pull/1213) (allocated-buffer scanout) remains open. This work targets a different FPGA and does not block the DE10-Nano plan.

### Release criteria

- **HIL:** a freshly flashed, identified DE10-Nano boots the exact release image to the expected FES screen, displays stable HDMI, accepts the documented wired and supported Bluetooth controllers, installs and runs each promoted package, loads the representative licensed/user-supplied firmware and media, returns cleanly from Stop, and preserves only the save data promised for that core. Check update and recovery behavior on the same named software/image combination. Record the image, bundle, package IDs/digests, source revisions, toolchain labels, controller models and results in dated validation evidence. Host tests, simulation, route timing, package seals and an older kit note are useful inputs but do not replace this exact-artifact HIL.
- **Image:** publish one reproducible, checksummed flashable image with a clean first boot and tested restore path. Keep the default profile closed around the menu/idle firmware; core packages remain separate downloads/selections. Verify the image and media receipts before HIL, then bind the HIL record to their hashes. Public first-run media must use per-device onboarding/configuration, not a developer's host token.
- **Toolchain labels:** show `OSS (Debian-style)` or `Quartus (non-free)` where a package is selected and in the release manifest. Never label a Quartus oracle/check as a shipped Quartus variant. Today, the expected label for registered products is OSS. Do not advertise both variants until the core's recipe, package identity, selector, and matched timing/seal gates implement the accepted policy.
- **Support wording:** publish a promoted-core list separately from Experimental, Demo, and Utilities. Each promoted system has exact-artifact checks for the media, firmware and controller features advertised. The matrix tier alone is not a support claim.

## 3. Visual polish

The repo already has a visual language, native renderer captures and a shared controller contract ([UX overview](../ux/README.md), [visual language](../ux/visual-language.md), [controller bindings](../../sources/FogCast/docs/rooms-controller-bindings.md)). Use that work to make one coherent product:

- **System identity and naming:** use “Sinclair ZX81,” “ColecoVision,” “Sega Master System,” and “Commodore 64” in user-facing shelves. Keep recipe IDs, package hashes, build names and diagnostic suffixes in Details or developer diagnostics. The plain-name work is part of open #1187.
- **Icons and artwork:** commission or create one original system icon per promoted model/family, with shared size, silhouette and contrast rules. Use game cover art only when supplied or legally usable. If no cover exists, keep the same card geometry and show the complete title, creator when known, and an identified system motif; never fabricate compatibility or ship unlicensed box art/ROMs. Show keyboard, controller, disk and firmware requirements as consistent readable marks.
- **Rooms and navigation:** keep Home → Systems/Library/Rooms/Settings consistent across keyboard, pointer and gamepad. Use one selected-item hierarchy and one meaning for Confirm, Details, Back and the system menu. Remove duplicate legacy rooms as the replacement system shelves land. Check 1280×720 and 1024×600, safe areas, long names and large text.
- **Readiness, error and empty states:** use labels and explanations, not color alone. Give loading, no media, missing firmware, unsupported format, offline host, disconnected controller, failed update and failed save distinct copy and an actionable next step. Preserve focus and selection when asynchronous metadata/art arrives. Show a useful empty-library action and a ROM-less first-play option.

## 5. Go-to-market

### Target users

**Assumption:** the first audience is technically confident DE10-Nano owners: existing MiSTer users interested in a small set of original/open cores, FPGA hobbyists who value an open Yosys/nextpnr route, and retro-computing/homebrew users who are comfortable supplying their own firmware and game media. Do not target plug-and-play console buyers until the folder, controller and update paths work without shell commands.

### Positioning against stock MiSTer

Position FES as a focused, open DE10-Nano FPGA platform with a package-based core catalog, a navigable tenfoot/room interface and an OSS build lane for its supported Cyclone V recipes. The project README itself notes that FES supports fewer systems than MiSTer and emphasizes its expansion/cartridge bus model and OSS toolchain. Do not claim MiSTer compatibility, equivalent breadth, drop-in core coverage, or universally open toolchains. Distinguish FES packages from stock MiSTer RBFs and say plainly which systems require user-supplied ROMs/firmware.

### Docs, website and quickstart

Keep developer build instructions in the existing [getting-started](../getting-started.md), [bootable-media](../bootable-media.md) and [development](../development.md) pages. Add an end-user quickstart linked from the README and a small release landing page with: supported board and image version; flash/checksum steps; first boot; controller and Bluetooth support; library folder layout; core install; legal firmware/ROM guidance; update/recovery; exact supported/experimental list; and troubleshooting. **Assumption:** the website host and owner are not specified in this repository; use the project-controlled public site if one exists, otherwise publish the initial landing page with the GitHub release/docs and keep it versioned here.

### Community channels

Use the GitHub release and Discussions/issues as the canonical download, changelog and support record. **Assumption:** announce a short demo and the same quickstart in the MiSTer community forum/Discord and retro-computing/homebrew communities, following each community's promotion rules. Ask for a bounded beta cohort focused on clean install, controller pairing, first game, media setup and update/rollback; collect reproducible reports with image/core version, not private ROMs or credentials.

### Release checklist

- Freeze the v1 catalog list and mark each system Supported, Experimental, Demo or Utility with its required ROM/firmware/media and its actual toolchain label.
- Build the named flashable image and kit-software bundle from reviewed source; capture hashes, reproducibility/verification receipts, package IDs and licenses/provenance.
- Confirm the public image has no developer config, token, ROM, firmware or unlicensed artwork. Provide checksums and a recovery image/path.
- Complete exact-image DE10 HIL: cold boot, HDMI, menu focus, wired and Bluetooth controller, library scan, install, launch, media, audio/input/video, Stop, save failure/retry where supported, system update, core update, rollback and reboot.
- Test a clean user profile with no preconfigured library and no network. Confirm the empty screen remains useful; after installing a ROM-less package such as Pong, confirm it still launches offline.
- Publish the quickstart, known limitations, update compatibility table, toolchain labels, supported-controller list and contact/support location.
- Tag the source and release artifacts together. Keep the observed hardware evidence class and its scope explicit; do not turn package, simulation or aggregate timing results into a release-image acceptance claim.

### Suggested timeline

**Assumption:** a six-week sequence after the support-matrix and tenfoot PRs are mergeable, with access to a DE10 test kit and a small number of contributors. This is gate-based; do not preserve dates by weakening criteria.

| Window | Milestone |
| --- | --- |
| Week 0 | Resolve the Uncertain list; align chosen package variants with the maintained support matrix; land the #1182 → #1187 UI stack; settle the OSS/Quartus presentation and no-ROM distribution policy. |
| Weeks 1–2 | Finish first-boot configuration, library/media wizard, controller setup and the public quickstart. Select the first exact core packages and close their user-flow blockers. |
| Weeks 3–4 | Produce the release image and package set; run clean-host checks, then exact-image HIL for install, first play, saves, update and recovery. Fix failures and rerun only affected evidence on final artifacts. |
| Week 5 | Publish a limited beta with the known-issues list; gather first-user results and resolve only release-blocking issues. Rebuild/retest any changed image or package. |
| Week 6 | Tag and publish GA if every release criterion passes; otherwise continue beta and move the date. Publish hashes, supported matrix, quickstart and rollback instructions together. |

## Assumptions and scope boundaries

- The first public target is DE10-Nano/Cyclone V; DE25-Nano/Agilex 5 is a separate product and Quartus Pro path.
- FES distributes no proprietary game ROMs or firmware. The owner supplies any required content unless a separate distribution license is documented.
- v1 uses the existing modular image/core architecture; this plan does not move playable cores into the default OS image.
- Website ownership, beta size, contributor availability and exact release date are not recorded in the repository. Timeline and channel recommendations above are assumptions.
- HIL claims apply only to the recorded image, software bundle, package and tested features. A later artifact needs its own acceptance.
