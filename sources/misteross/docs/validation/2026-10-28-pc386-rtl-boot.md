# pc386 boot on the RTL CPU

Originally recorded 2026-10-28; refreshed 2026-10-29. Host simulation only. No package, RBF or kit.

The first step of pc386's M5, "the RTL CPU in the machine"
([design](../pc386-machine-design.md)): the machine simulation's FreeDOS boot,
run with the current [`fes_i386_cpu`](../../cores/fes-common/rtl/i386/) in
place of the Bochs oracle. This refresh measures the boot and stop path after
the register-form BT/BTS/BTR/BTC implementation landed. The stop-path run below
was refreshed again after DAA and the other BCD-adjust instructions were built.

- The refreshed FreeDOS RTL boot and oracle control ran on 2026-10-29 at bench
  revision `a0595dcf098b` with CPU revision `015048c65d19`
  ([#1194](https://github.com/DeanoC/fes/commit/015048c65d198a32c96908624d4a2f4caf12ad4c)). The RTL boot uses the
  prompt gate from [`2ecb7b4`](https://github.com/DeanoC/fes/commit/2ecb7b4cf1c244a34a1658fa0dbc8ae72cab7904).
- The `rtl-stops` suite was rerun on 2026-10-29 at bench revision
  `c817b01842fd` with CPU revision `457ec7de4ae3`
  ([#1199](https://github.com/DeanoC/fes/commit/457ec7de4ae35a11b4c9c067cab25f722e6ee89a)). Its results replace the
  earlier stop-disk runs in this record.
- The FreeDOS 1.4 fixture of [`freedos.lock`](../../cores/fes-pc386/sim/freedos.lock)
  (KERNL386.SYS 2043, FreeCOM 0.86a), with the locked Bochs BIOS and LGPL
  VGABios. The boot suite types `dir` at the prompt and needs its listing.
- The retained oracle instruction census is the older run `fe83f0e522` on CPU
  revision `592be15ebf`; it runs no RTL and was not rerun in this refresh.
- Run data: [`2026-10-28-pc386-rtl-boot.jsonl`](2026-10-28-pc386-rtl-boot.jsonl):
  the two refreshed boot runs, the current `rtl-stops` run, and the retained
  census with its per-stem rows.

## Result

**FreeDOS boots on the RTL CPU to `C:\>`, and `dir` lists the disk.** The
current run's final screen matches the oracle boot character for character.
Nothing stopped the RTL: no unbuilt encoding, no fault during a delivery, no
stall. During the RTL boot, the oracle ran no instructions.

The retained 2026-10-28 oracle census reports 103,831,340 retired
instructions across 281 stems, all in real mode. That census used CPU revision
`592be15ebf` and was not rerun for this refresh; current-run stop and prompt
results are recorded separately above and below.

| | Oracle | RTL |
| --- | ---: | ---: |
| Instructions | 103,831,426 steps (86 interrupt deliveries) | 121,487,313 retired, 0 on the oracle |
| `C:\>` first shown | 2.400 s (cycle 240,003,758) | 2.350 s (cycle 235,000,046) |
| Run end (`dir` listed, prompt back) | 4.300 s | 4.100 s |
| ISA I/O, every access at its class time | isa8 75,597 at 74 clocks; isa16 209,152 at 38 | isa8 76,365 at 74 clocks; isa16 209,152 at 38 |
| INTA, all at 146 clocks | 86 | 82 |
| VGA port writes, every access at its class time less its FIFO waits | 823 bytes at 4 clocks; 3,381 words at 7; none waited | 823 at 4; 3,381 words at 7; 4 word writes waited 6 clocks each |
| VGA trace: MMIO reads, writes; port writes, reads | 28,815; 52,209; 4,204; 6 | 28,837; 52,209; 4,204; 6 |
| VGA trace replay against Bochs's VGA | match; 85,234 events, 0 replay/read/VRAM/frame mismatches, 0 differing end-VRAM bytes | match; 85,256 events, 0 replay/read/VRAM/frame mismatches, 0 differing end-VRAM bytes |

The boot is paced by the timer, not the CPU: its delays count PIT ticks, so
a faster CPU retires more instructions in the same simulated time. The RTL
takes about 3.4 clocks an instruction here, I/O included, with every fetch
and load hitting; the oracle model takes 4, plus its I/O. That is no
measure of the CPU, since there are no caches yet (below).

## The design's known gaps, in this boot

| Gap | What the boot did |
| --- | --- |
| No caches | Not exercised: the bench's memory has no latency. The boot's clocks are no evidence about them |
| No self-modifying-code detection | 425,402 stores landed in code the front end had already fetched ahead of the next instruction, on two bytes: 99EFBh (8FE9:A06B), from code at 8FE9:A04A from 0.30 s, and 12C30h, from code at 1006:2BAE at 2.28 s. No instruction then retired over a stored byte before the front end refetched: both are data inside code segments. Within the check's window, nothing in the boot modifies code it then runs |
| No protected mode | Never entered. The retained census has no protected-mode or V86 instruction; nothing calls INT 15h AH=87h or 89h, since the fixture loads no XMS driver |
| No debug traps | TF was never set (0 retirements with TF); no MOV to a debug register |
| No double fault | No fault during a delivery |

Two more things showed up:

- **No uncached path.** The RTL's VGA trace has 22 MMIO reads the oracle's
  does not, all in A0000h-AFFFFh, which text mode leaves unmapped (each read
  FFh); its writes and port accesses are the oracle's, in number. They are
  the RTL's 22 VGA loads whose uop never retired, every one on a wrong path
  behind a redirect that retired: `ADD r/m8, r8` (`00h`) decoded from the
  zero bytes after a BIOS `JMP` at F000:E3FE (6 at each of E401 and E403)
  and after an `IRET` at F000:FEE6 (4 at each of FEE7 and FEE9) and at
  F000:F84B (1 at each of F84C and F850). They reach the VGA because the CPU
  has no uncached path yet; the design's uncached loads wait until they are
  the oldest. In text mode they change nothing. In mode 13h, mode X or
  planar modes such a load would load the VGA's latches, so the games need
  that path. 11 of the 22 died on the edge M1 sent them, and no later load
  was issued before their reads came back, so the bench's handling of such
  a load (below) made no difference to this boot.
- **VGA port writes wait for FIFO space.** A VGA port write completes when
  its bytes are in the VGA's front FIFO, which it shares with MMIO writes.
  The RTL posts VGA stores into that FIFO as they retire, one a clock, so an
  OUT can follow them while the FIFO is full; the oracle path's stores never
  come close enough to fill it. The exact `vga-out` check assumed room, and
  4 of the RTL's 3,381 word writes took 13 clocks, not 7. The bench now
  counts the clocks each VGA port write's byte waits against a full FIFO
  (`sim/pc386_vga.vlt` observes the VGA's `io_new` and `fifo_full`), reports
  them as `IOWAIT` and takes them out of the access's time, which must still
  be the class time. Those 4 waited 6 clocks each and are 7 net. The bench
  also issues an I/O access only once the machine has taken every older VGA
  store, as the design's I/O instructions drain the write buffer. Before it
  did, word writes took up to 109 clocks, byte writes up to 9, and the trace
  replay fell behind the trace, since an OUT overlapped the stores before it.

## The stop path

The boot never stopped, so the stop test disk
([`rtl_stop_test.asm`](../../cores/fes-pc386/sim/rtl_stop_test.asm),
`--suite rtl-stops`) checks the path on instructions this CPU commit has not
built. It boots the disk on both CPUs:

| | |
| --- | --- |
| Port E9h, oracle | `R 10 46`, `R 55 86`, `DONE` |
| Port E9h, RTL | `R 10 46`, `R 55 86`, `DONE` |
| Stops | SMSW (`0F01.4`): 2 stops at 2 sites, LMSW (`0F01.6`): 1 stop at 1 site; each gap ran on the oracle |
| Protected mode | One stretch of 3 oracle steps, from after LMSW to MOV CR0 clearing PE; then the RTL restarts in real mode |
| RTL | 4,221,578 retired, 6 on the oracle, to `DONE` at 0.185 s |

The oracle and RTL produce the same E9 bytes. The suite passes. One of the
RTL's 763 VGA port word writes waited 6 clocks for FIFO space and completed in
7 clocks.

## What comes next for Phase 3

This boot touched none of the known gaps, so the next measurements are the
games, each with `--census` under the oracle and then on the RTL:

- Wolfenstein 3D and Ultima VI run in real mode, in mode X and mode 13h,
  where wrong-path VGA loads would load the latches: the uncached path
  comes before them.
- Ultima VII's Voodoo memory manager enters unreal mode, and an XMS driver
  needs INT 15h AH=87h: both need protected-mode entry (LGDT, MOV CR0 or
  LMSW, segment loads from descriptors), which nothing here exercised.
- The runner takes `--cpu rtl` for the boot suite only; the game and sound
  suites need it too.

## How the bench runs the RTL

`machine_tb --cpu rtl` (`scripts/sim_fes_pc386.py --suite boot --cpu rtl`)
clocks the CPU with the machine, one system clock at a time, as the
lockstep's `Rtl` class drives it:

| CPU port | In the machine |
| --- | --- |
| Fetch (`mem_block`) | Guest memory, no latency: the block as memory held it on the requesting edge |
| Data (`dmem_*`) | Guest memory, no latency; the retiring store writes before the load reads |
| VGA window A0000h-BFFFFh | Stores post in order to the machine's MMIO port as they retire; a load waits for its bytes, reading only those it uses, with byte enables (`sim/pc386_rtl_cpu.sv` exports the load's size). A load whose uop dies on the edge M1 sends it still reads the VGA, and its bytes go to no later load |
| I/O (`io_req`/`io_ack`) | The AT core's I/O port, one access at a time, with its device time, once every older VGA store is taken |
| INTA, INTR | The AT core's PICs; NMI is tied low |
| A20M | Masks physical bit 20 below the reset alias at FFFF0000h |

When the CPU stops on an encoding it has not built (`trace_unimplemented`),
the bench records the stop by stem in the lockstep's naming, hands the RTL's
architectural state to the oracle (with the oracle's own CR0, GDTR, IDTR and
the like), lets it run that one instruction, and restarts the RTL from the
oracle's state after it, by reset with `init_*`. Posted VGA stores reach the
VGA first, and pages the RTL stored to are invalidated in the oracle. If the
oracle is then in protected mode or V86, it keeps running until it is back
in real mode, and the stretch is recorded. A fault during an exception's
delivery (the double-fault case) ends the run, since part of the delivery
has retired. So does a halt with IF clear, as on the oracle path. No
retirement for 0.1 s counts as a stop too (a stall).

While the CPU waits for an I/O or INTA cycle at the AT core, or sits in HLT
with INTR low, and has made no request for 16 clocks, only the machine is
clocked. The CPU is frozen then, so this changes nothing it does: the first
0.02 s retire the same 282,906 instructions either way.

The SMC check: a store into a block the front end has fetched, ahead of the
next instruction and within 96 bytes of it, is counted, and so is an
instruction that then retires over a byte so stored before the front end
next fetches out of sequence. It sees only what is within that window.

The bench follows each VGA load through M2, EX and WB, from what
`sim/pc386_rtl_cpu.sv` reports of each edge (whether the stages moved, WB
committed and WB flushed), and counts the loads whose uop never retired: on
a wrong path behind a redirect that retired, in an instruction a fault or an
interrupt restarted, or behind a stop. `UNRETIRED` lines name their
instructions. A Wolfenstein 3D run on the RTL (the game census work,
branch `deano/pc386-game-census`) found that the port used to give the bytes
of a load whose uop died on its sending edge to the next load: the game's
mode-X copy lost a load as IRQ0 was taken, and the read's byte became the
high byte of vector 8's IP. Such a load now gives its bytes to no load.
`vga_cancelled` counts them, and `vga_overlaps` the loads issued while one's
read was out.

`--census F` counts every instruction the oracle retires by stem; on the
oracle path that is the whole boot's instruction mix.

Limits of the bench, not of the CPU:

- Memory has no latency, so the RTL's cycle counts are those of a CPU whose
  every fetch and load hits. There is no L1, L2 or write buffer yet.
- Nothing compares the RTL with the oracle as the machine runs; the RTL's
  instructions rest on the lockstep corpus. A wrong result would show as a
  boot that goes astray, not as a stop. This one did not.
- The RTL boot took 22 CPU minutes (one thread) on Powerboat; with the box
  more loaded it has taken 31, and 42 (61 minutes wall at a load of 35 to
  110 on 24 threads). The oracle boot took 8 CPU minutes, the oracle census
  run 18.

## Reproduce

```sh
python3 scripts/sim_fes_pc386.py --suite boot --cpu rtl --download  # the gated RTL FreeDOS boot
python3 scripts/sim_fes_pc386.py --suite rtl-stops --download       # the oracle-backed stop suite
python3 scripts/sim_fes_pc386.py --suite boot --download            # the oracle FreeDOS boot
```

The census is `machine_tb --census FILE` on the oracle boot's arguments
(`--disk build/sim/fes-pc386/freedos.img --limit-seconds 8 --type 'dir|'
--expect 'bytes free'`).
