# pc386 boot on the RTL CPU

Dated record, 2026-10-28. Host simulation only. No package, RBF or kit.

The first step of pc386's M5, "the RTL CPU in the machine"
([design](../pc386-machine-design.md)): the machine simulation's FreeDOS boot,
run with [`fes_i386_cpu`](../../cores/fes-common/rtl/i386/) in place of the
Bochs oracle, to see how far it gets and what stops it. Nothing in the CPU
changed; what it lacks belongs to the i386 slices.

- The CPU is `592be15ebf`, the tip of the i386 stack (`deano/i386-bits`,
  [#1185](https://github.com/DeanoC/fes/pull/1185)) when the runs were made,
  byte for byte, with pc386 M2 and M3 from main merged in. The branch has
  since taken the stack's own merge of main (`1814f0c590`), whose CPU RTL
  differs from `592be15ebf` only in comments.
- The FreeDOS 1.4 fixture of [`freedos.lock`](../../cores/fes-pc386/sim/freedos.lock)
  (KERNL386.SYS 2043, FreeCOM 0.86a), with the locked Bochs BIOS and LGPL
  VGABios. The boot suite types `dir` at the prompt and needs its listing.
- The RTL boot and the stop test are of `a53cded03d`, through
  `scripts/sim_fes_pc386.py`. The census is of `fe83f0e522`, whose oracle
  path is the same.
- Run data: [`2026-10-28-pc386-rtl-boot.jsonl`](2026-10-28-pc386-rtl-boot.jsonl):
  a summary line per run and the census, a line per stem.

## Result

**FreeDOS boots on the RTL CPU to `C:\>`, and `dir` lists the disk.** The
final screen is the oracle boot's, character for character. Nothing stopped
the RTL: no unbuilt encoding, no fault during a delivery, no stall. The
oracle ran no instruction of the boot.

So the ranking of what FreeDOS needs from the CPU is empty for this boot.
The oracle census of the same boot shows why: 103,831,340 instructions of
281 stems, all in real mode, and every stem is one the lockstep counts as
built (`test_fes_i386_lockstep.py`'s `SCOPE`). The boot uses no BCD adjust,
no BOUND, no x87 or WAIT, no `0F 00`/`0F 01` system instruction, no MOV to
or from a control or debug register, no BT by a register, no 67h-prefixed
form and no HLT.

| | Oracle | RTL |
| --- | ---: | ---: |
| Instructions | 103,831,426 steps (86 interrupt deliveries) | 121,487,313 retired, 0 on the oracle |
| `C:\>` first shown | 2.400 s (cycle 240,003,758) | 2.350 s (cycle 235,000,046) |
| Run end (`dir` listed, prompt back) | 4.300 s | 4.100 s |
| ISA I/O, every access at its class time | isa8 75,597 at 74 clocks; isa16 209,152 at 38 | isa8 76,365 at 74; isa16 209,152 at 38 |
| INTA, all at 146 clocks | 86 | 82 |
| VGA trace: MMIO reads, writes; port writes, reads | 28,815; 52,209; 4,204; 6 | 28,837; 52,209; 4,204; 6 |
| VGA trace replay against Bochs's VGA | match, 85,234 events | match, 85,256 events |

The boot is paced by the timer, not the CPU: its delays count PIT ticks, so
a faster CPU retires more instructions in the same simulated time. The RTL
takes about 3.4 clocks an instruction here, I/O included, with every fetch
and load hitting; the oracle model takes 4, plus its I/O. That is no
measure of the CPU, since there are no caches yet (below).

## The design's known gaps, in this boot

| Gap | What the boot did |
| --- | --- |
| No caches | Not exercised: the bench's memory has no latency. The boot's clocks are no evidence about them |
| No self-modifying-code detection | 425,402 stores landed in code the front end had already fetched ahead of the next instruction, on two bytes: 99EFBh (8FE9:A06B), from code at 8FE9:A04A from 0.30 s, and 12C30h, from code at 1006:2BAE at 2.28 s. No instruction then retired over a stored byte before the front end refetched: both are data inside code segments. Within the check's window, nothing in the boot modifies code it then runs |
| No protected mode | Never entered. The census has no protected-mode or V86 instruction; nothing calls INT 15h AH=87h or 89h, since the fixture loads no XMS driver |
| No debug traps | TF was never set (0 retirements with TF); no MOV to a debug register |
| No double fault | No fault during a delivery |

Two more gaps showed up:

- **No uncached path.** The RTL's VGA trace has 22 MMIO reads the oracle's
  does not, all in A0000h-AFFFFh, which text mode leaves unmapped (each read
  FFh); its writes and port accesses are the oracle's, in number. They are loads on a wrong path, which reach the VGA because the CPU
  has no uncached path yet; the design's uncached loads wait until they are
  the oldest. In text mode they change nothing. In mode 13h, mode X or
  planar modes such a load would load the VGA's latches, so the games need
  that path.
- **The VGA port write timing check.** The boot suite fails one check, and
  only under the RTL: every `vga-out` word write must take exactly 7 clocks,
  and 4 of the RTL's 3,381 took 13. A VGA
  port write completes when it is in the VGA's FIFO, which it shares with
  MMIO writes. The RTL posts VGA stores into that FIFO as they retire, one a
  clock, and an OUT can follow them while the FIFO is full; the oracle path's
  stores never came close enough to fill it. The bench issues an I/O access
  only once the machine has taken every older VGA store, as the design's I/O
  instructions drain the write buffer. Before it did, word writes took up to
  109 clocks, byte writes up to 9, and the trace replay fell behind the trace,
  since an OUT overlapped the stores before it. The check's rule assumes the
  FIFO has room. It is left as it is: whether RTL runs get a rule that allows for a
  full FIFO is Deano's call. `isa8`, `isa16`, INTA and `vga-in` pass.

## The stop path

The boot never stopped, so the stop test disk
([`rtl_stop_test.asm`](../../cores/fes-pc386/sim/rtl_stop_test.asm),
`--suite rtl-stops`) checks the path on instructions this CPU commit has not
built. It boots the disk on both CPUs:

| | |
| --- | --- |
| Port E9h, oracle | `R 20 12`, `R 00 57`, `R 55 86`, `DONE` |
| Port E9h, RTL | the same |
| Stops | DAA (`27`) 2 at 2 sites, SMSW (`0F01.4`) 1, LMSW (`0F01.6`) 1; each run on the oracle |
| Protected mode | One stretch of 3 oracle steps, from after LMSW to MOV CR0 clearing PE; then the RTL restarts in real mode |
| RTL | 4,221,628 retired, 7 on the oracle, to `DONE` at 0.185 s |

The DAA results and flags, and the AL the RTL writes after the stretch, are
the oracle's. The suite fails only the same `vga-out` class: one word write
of 763 took 13 clocks.

## What comes next for Phase 3

This boot touched none of the known gaps, so the next measurements are the
games, each with `--census` under the oracle and then on the RTL:

- Wolfenstein 3D and Ultima VI run in real mode, in mode X and mode 13h,
  where wrong-path VGA loads would load the latches: the uncached path
  comes before them.
- Ultima VII's Voodoo memory manager enters unreal mode, and an XMS driver
  needs INT 15h AH=87h: both need protected-mode entry (LGDT, MOV CR0 or
  LMSW, segment loads from descriptors), which nothing here exercised.
- The runner takes `--cpu rtl` for the boot suite only; the game and sound
  suites need it too.

## How the bench runs the RTL

`machine_tb --cpu rtl` (`scripts/sim_fes_pc386.py --suite boot --cpu rtl`)
clocks the CPU with the machine, one system clock at a time, as the
lockstep's `Rtl` class drives it:

| CPU port | In the machine |
| --- | --- |
| Fetch (`mem_block`) | Guest memory, no latency: the block as memory held it on the requesting edge |
| Data (`dmem_*`) | Guest memory, no latency; the retiring store writes before the load reads |
| VGA window A0000h-BFFFFh | Stores post in order to the machine's MMIO port as they retire; a load waits for its bytes, reading only those it uses, with byte enables (`sim/pc386_rtl_cpu.sv` exports the load's size) |
| I/O (`io_req`/`io_ack`) | The AT core's I/O port, one access at a time, with its device time, once every older VGA store is taken |
| INTA, INTR | The AT core's PICs; NMI is tied low |
| A20M | Masks physical bit 20 below the reset alias at FFFF0000h |

When the CPU stops on an encoding it has not built (`trace_unimplemented`),
the bench records the stop by stem in the lockstep's naming, hands the RTL's
architectural state to the oracle (with the oracle's own CR0, GDTR, IDTR and
the like), lets it run that one instruction, and restarts the RTL from the
oracle's state after it, by reset with `init_*`. Posted VGA stores reach the
VGA first, and pages the RTL stored to are invalidated in the oracle. If the
oracle is then in protected mode or V86, it keeps running until it is back
in real mode, and the stretch is recorded. A fault during an exception's
delivery (the double-fault case) ends the run, since part of the delivery
has retired. So does a halt with IF clear, as on the oracle path. No
retirement for 0.1 s counts as a stop too (a stall).

While the CPU waits for an I/O or INTA cycle at the AT core, or sits in HLT
with INTR low, and has made no request for 16 clocks, only the machine is
clocked. The CPU is frozen then, so this changes nothing it does: the first
0.02 s retire the same 282,906 instructions either way.

The SMC check: a store into a block the front end has fetched, ahead of the
next instruction and within 96 bytes of it, is counted, and so is an
instruction that then retires over a byte so stored before the front end
next fetches out of sequence. It sees only what is within that window.

`--census F` counts every instruction the oracle retires by stem; on the
oracle path that is the whole boot's instruction mix.

Limits of the bench, not of the CPU:

- Memory has no latency, so the RTL's cycle counts are those of a CPU whose
  every fetch and load hits. There is no L1, L2 or write buffer yet.
- Nothing compares the RTL with the oracle as the machine runs; the RTL's
  instructions rest on the lockstep corpus. A wrong result would show as a
  boot that goes astray, not as a stop. This one did not.
- The RTL boot costs about 42 CPU minutes (one thread); it took 61 minutes
  on Powerboat at a load of 35 to 110 on 24 threads. The oracle census run
  took 18 CPU minutes.

## Reproduce

```sh
python3 scripts/sim_fes_pc386.py --suite boot --cpu rtl   # writes build/sim/fes-pc386/boot-rtl/
python3 scripts/sim_fes_pc386.py --suite rtl-stops        # writes build/sim/fes-pc386/rtl-stops/
python3 scripts/sim_fes_pc386.py --suite boot             # the oracle boot
```

The census is `machine_tb --census FILE` on the oracle boot's arguments
(`--disk build/sim/fes-pc386/freedos.img --limit-seconds 8 --type 'dir|'
--expect 'bytes free'`).
