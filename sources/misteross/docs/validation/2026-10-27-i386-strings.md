# i386 strings: MOVS, CMPS, STOS, LODS and SCAS with REP, and ENTER

Dated record, 2026-10-27. Host simulation and routed diagnostics on Powerboat.
No package, RBF or kit.

After [the seq holds](2026-10-27-i386-seqhold.md), this slice builds the
real-mode string instructions and ENTER on a string engine in D, as the
design's string sequencer describes. It covers:
- MOVS, CMPS, STOS, LODS and SCAS: byte, word and dword, both address sizes,
  a source segment override, DF, and REP, REPE and REPNE;
- ENTER at every nesting level, on either stack width and operand size.

Run data: [`2026-10-27-i386-strings.jsonl`](2026-10-27-i386-strings.jsonl).
- The before figures are the seq holds' `670cc7ac93` (its record's rows).
- Routes are of `e9f610d0a8`. Its RTL is the branch's but for a README
  change.
- The full lockstep runs are of `9815be2121`. The commits after it add two
  directed cases, which were run on both the RTL and the netlist, plus docs
  and unit tests.
- Eight nextpnr seeds. A Quartus row's `fingerprint` is the first 12 hex
  digits of the SHA-256 of its `sources` map, as JSON with sorted keys.

## The string engine

While a string instruction or ENTER runs, D keeps copies of the next source
and destination offsets and of the count (`r_src`, `r_dst`, `r_cnt`), and
ENTER's frame pointer (`r_fp`).
- Each step's address is a copy, which the step then moves on. The uops so
  issue from `dc` one per cycle, with no forwarding behind them.
- An offset wraps at its address's width: the instruction's address size
  for a string, the stack's for ENTER.
- `fes_i386_seq` builds every step from the instruction's first uop, as
  for the fixed sequences, and from whether D's copy of the count is 0, 1
  or 2.

**A string's first uop** is a NOP that loads the copies from ESI, EDI and
ECX (CX by address size). It waits in D until:
- those are in registers;
- no older uop that writes DF is in AG to EX, so EX's running flags hold
  the DF the string runs with;
- neither its source segment nor ES is being written.

It also keeps the next instruction's linear address (`s_tgt`) for REPE and
REPNE. Under REP the string runs one element per count, else one. A REP
with a count of 0 is a NOP that ends the instruction.

**The elements:**

| Instruction | Uops per element | What each does |
| --- | --- | --- |
| STOS | 1 | Store eAX at ES:EDI |
| LODS | 1 | Load eAX from seg:ESI |
| SCAS | 1 | Compare eAX with ES:EDI |
| MOVS | 1 | Load seg:ESI, store the value at ES:EDI (`st2`) |
| CMPS | 2 | seg:ESI's value as a result; its compare with ES:EDI |

- **MOVS's store address** is a second address, which D computes from the
  destination copy and checks against ES's limit. M1 raises that fault after
  the load's own, so a source that faults wins, as on the 386.
- **CMPS's compare** takes the first uop's result one stage ahead, from the
  WB register, as a pending operand does. D issues it in the cycle after the
  first uop: nothing it waits on can change between them, which is why the
  first uop waits for both segments.
- **Each element's last uop steps ESI, EDI and ECX at WB.** A fault part way
  leaves them at the elements done, with EIP at the instruction, as the 386
  does. No forwarding sees the steps, so a uop that reads ESI, EDI or ECX
  waits in D while an element that steps it is in AG to WB.
- **REPE and REPNE CMPS and SCAS** issue elements ahead of the flag result.
  An element but the last ends the instruction when its compare's ZF says
  so. It does that as a taken branch to the next instruction, so WB flushes
  the elements behind it, and their loads fault only if they would retire.

**M2 takes a load's bytes from a MOVS store in EX.** A MOVS element's store
data is its own load, which is in EX when the load behind it is in M2. So D
does not hold a load behind a MOVS store, M2 takes the bytes from EX's
loaded value ahead of the store in WB, and REP MOVS runs an element a cycle.
Any other store still holds the load behind it a cycle.

**ENTER** runs on the same engine:
1. Its first uop pushes EBP at SS:ESP less the size, ESP unmoved. It loads
   the source copy (EBP less the size), the destination copy (ESP less
   twice the size) and the frame pointer (ESP less the size, its high half
   ESP's on a 16-bit stack).
2. The level (mod 32) less one uops each copy a slot below EBP to the next
   push slot, as a MOVS element does.
3. Unless the level is 0, one uop pushes the frame pointer.
4. The last uop writes EBP from the frame pointer and ESP from the next push
   slot plus the size less imm16. It loads the slot at that ESP, a limit
   check only, as the 386EX does.

ESP and EBP change only at the last uop, so a fault before it leaves them,
with the pushes before it written. That is what Bochs does, and the corpus
agrees on every ENTER state. ENTER is not in the ROM: its loop is the
engine's count.

## Rates

Latency-free, in the lockstep testbench, from runs of 64 and 128 elements:

| | Cycles |
| --- | --- |
| REP MOVS, STOS, LODS, SCAS (any size) | 1 per element |
| REP MOVSB copying over itself (DI = SI + 1) | 1 per element |
| REP CMPS | 2 per element |
| A string's start | 1 (LODSB, STOSB, MOVSB: 1 cycle more than a NOP) |
| ENTER imm16, level | 2 more than a NOP at level 0, 3 at level 1, the level plus 3 above (31: 34) |
| A reader of ESI, EDI or ECX right after a string | 5 more than after another instruction |
| A REPE or REPNE that ends early | a taken branch's refetch |

**Quartus averages 99.8 MHz against 102.1**, Q-limited on all four seeds.
Q is the front end, which this slice does not change. DC and D stay above it.

**nextpnr loses 8.5 MHz**, to 61.7, and DC limits six seeds.
- **Every seed's critical path** starts at dops' `ready` registers and runs
  through a GPR's value as D selects it.
  - On seeds 1-3, 5 and 8 it ends in `dc` or AG's register. It runs through
    the count's compares with 0, 1 and 2 (its nets name `r_cnt`) and
    `fes_i386_seq`'s first element: whether the string ends there, or is a
    NOP. That is the first uop deciding its next step from ECX as
    forwarded.
  - On seeds 6 and 7 it ends at ENTER's copies (`r_dst`, `r_fp`), through
    the select by register number and a subtract.
  - On seed 4 it ends in AG's register, through LUTs whose names do not say
    which path.
- **The netlist's deepest D path** is 11 LUT levels against 9, ending at
  `r_dst`.
- **Every stage fell**, by 5-12 MHz: the design is 12% larger (below), and
  the same device places it worse.
- The issue-loop cut is next. It builds the first element without the count
  and latches the copies from fixed registers, with no cycle changed.

- **The string files** are 32 SingleStepTests files, 80,000 states, with REP
  counts 0-63. Of those, 4,586 fault part way (#UD for LOCK, #GP and #SS at
  the limit) and run on into the handler.
- **The four rep-overwrites-own-encoding states** store over the HLT after
  the REP. The RTL halts on the HLT it had fetched and matches the corpus's
  final state. That needed the lockstep change below.
- **Two directed ENTER cases.** One faults only at the check of its final
  slot, with SP at FFFFh. The other is ENTER 0, 2 at SP 5, whose frame
  pointer's push straddles the wrap and whose #SS delivery faults again.

**Lockstep changes:**
- **An entry that leaves every field to the corpus** now lets the RTL's halt
  stand, as it let its fault stand.
- **A double fault.** Each oracle event counts the writes before it. After
  the RTL stops, every byte it wrote must be one the oracle wrote before its
  delivery began, with the oracle's value unless the oracle's partial frame
  wrote it again. The RTL may write less: its far CALL and INT check their
  slots before they push, which Bochs does not. A string's ESI, EDI, ECX,
  eAX and arithmetic flags are the oracle's.
- **The random programs** get string blocks and ENTER / LEAVE frames.
  - A quarter of the string blocks are REP MOVS or CMPS over two seeded
    words, copying over themselves, with ES = DS set just before.
  - String blocks fence backward jumps, which reran a REP with whatever CX
    held.
- **Gaps and limits.** Anything within five instructions after a string
  has its own gap bucket. An event may take 4,000 cycles, and
  `FES_I386_FIRST` reruns one random program.

**Mutations**, each on the 32 string and ENTER files and 2 × 200 random
programs (with the two directed ENTER cases for the last):

## What the design doc should say

This is reported for the doc's owner to write; the doc is unchanged here.

- **The string sequencer is D's string engine.** D's copies make each
  element's address a register in D. The steps reach ESI, EDI and ECX at
  WB, element by element, with no forwarding. What follows waits for them
  (5 cycles for a reader), a cost the design's "consistent between
  elements" leaves open.
- **MOVS is one uop with two addresses**, as the design says. The second's
  limit check is D's, and M2 takes a load's bytes from a MOVS store in EX,
  so REP MOVS needs no load hold. CMPS is two uops, so REP CMPS runs at half
  the rate of the others.
- **REPE and REPNE end early as a taken branch** to the next instruction:
  the elements behind it are flushed, as the design says. The refetch costs
  what a taken branch does.
- **ENTER is on the string engine, not the ROM.** It writes ESP and EBP
  only at its end, after checking the final slot, as the 386EX does.
- **Interrupts between elements** are not built: there are no interrupts
  yet.
- **Self-modifying code.** Four corpus states store over the HLT after a
  REP STOS or MOVS. The RTL, which has no self-modifying-code check yet,
  runs the HLT it had already fetched, as the 386EX did (the divergence
  rep-overwrites-own-encoding follows the corpus). Under the design's
  default `coherent` profile the RTL would refetch and run the new bytes
  instead, as Bochs does. Those states then need the `queue16` profile, or
  a divergence for the profile.
