# i386 memory path: L1I, L1D and the bus interface on DDR port 0

Dated record, 2026-10-28, with Quartus fits added 2026-10-29. Host
simulation, Quartus fits and routed diagnostics on Powerboat and the CUDA
route host. No package, RBF or kit.

The first [memory slice](../i386-cpu-design.md#memory-slices):
`fes_i386_cpu` reaches guest memory through its own L1I, L1D and bus
interface on HPS DDR port 0, instead of the ideal fetch and data ports the
benches served. It is stacked on the bit test by a register slice
([#1194](https://github.com/DeanoC/fes/pull/1194)) with the pc386 RTL boot
([#1195](https://github.com/DeanoC/fes/pull/1195)) merged in, which brings
`machine_tb --cpu rtl`.

Run data: [`2026-10-28-i386-memory-path.jsonl`](2026-10-28-i386-memory-path.jsonl),
each row's `state` one of `before` (the base, `b84add5c66`), `first` (the
slice as first built, `675fd13add`), `after` (this slice, `c4b9663d64`) and
`review-fix` (its review fix, `c1b4a10db9`, with the lockstep at
`377a2be4b0`).
A Quartus row's `flow` is `quartus` and its `record` is `post_map` or `fit`,
in the shape of the [Quartus DSP record](https://github.com/DeanoC/fes/blob/06079439c2/sources/misteross/docs/validation/2026-10-28-i386-quartus-dsp.md)'s
rows.

**Result:**
- The RTL and the Yosys netlist pass the full lockstep with the port-0
  model, the MMIO window and mixed memory: 1,734,099 corpus states, 32,000
  random programs, and DMA, FLUSH and store-to-load forwarding cases
  ([Checks](#checks)). Two reviews found three faults in M2's store merge,
  now fixed: stores to read-only RAM, holes and devices forwarded, and the
  merge compared linear addresses ([The review fix](#the-review-fix)).
- FreeDOS boots on the RTL CPU through the new path, its VGA reads exactly
  the oracle's: no load reaches MMIO on a wrong path
  ([FreeDOS](#freedos-on-the-rtl-cpu-through-the-new-path)).
- Quartus 17.0.2, the i386's timing reference, fits it at 100.3 MHz on
  average against the base's 102.2, with muldiv's products in DSP blocks at
  a 120 MHz target ([Quartus](#quartus)). Q's aligner still limits most
  seeds. The L1I's hit select into F1 limits one. The review fix fits at
  98.2: its own logic costs nothing measurable, and the L1I's hit select
  falls 3 to 4 MHz and limits two seeds.
- nextpnr routes it at 48.3 MHz against the base's 61.5, measured and kept
  as data ([nextpnr routes](#nextpnr-routes)). The first build routed at
  36 MHz: D to WB's freeze waited on the L1D's tag compare. The L1D now
  decides its hit in M1 and every freeze input is one register. The rest of
  nextpnr's gap is wire, which belongs to the nextpnr project after
  bring-up.

## What the slice builds

- **L1I** (`fes_i386_l1i`): 16 KiB, 4 ways, 32-byte lines, indexed by linear
  bits 11:5 and tagged with the physical page, F2's compare in eight
  replicated hit sets as the front-end spike had it. Valid bits are
  flip-flops. A miss fills its line from port 0; a fill ends only with no
  store in EX or WB, and a store into its line while it fills, a DMA write or
  FLUSH spoils it. Each store reads a snoop copy of the tags as it enters WB,
  and on the edge after its commit a register clears a way holding its line.
  Fetches from MMIO or a hole read FFh.
- **L1D** (`fes_i386_l1d`): 16 KiB, 4 ways, two dword banks, write-through,
  no write allocate. The lookup tags are read for AG's address as a uop
  enters M1; M1 compares them and registers the hit, and M2 selects the way
  ([Timing](#timing) says why). A cacheable load that hits inside its line
  returns in M2; a miss, a line-crossing access, MMIO and holes take a slow
  path with D to WB frozen, which also fills the line on a miss. Stores
  update a way holding their line at commit, found in a probe copy of the
  tags read as the store enters WB and re-read after a fill.
- **Bus interface** (`fes_i386_biu`): four 32-byte line entries with byte
  masks, filled from a commit register a cycle after a store retires,
  coalescing RAM bytes into the newest entry; MMIO bytes get entries of their
  own, posted in order; read-only RAM and holes drop stores. Line
  reads wait for the entries holding their line, MMIO reads and I/O for the
  whole buffer. DMA (the machine's byte port) goes through port 0 in the
  buffer's order and clears both L1s' set on a write; FLUSH empties the
  buffer and clears both L1s. A store in WB waits while the buffer will not
  have two entries free once the store ahead of it has entered (`st_wait`, a
  sixth freeze input).
- **Attributes**: the design's attribute map as an input (640 KiB to 1 MiB
  in 16 KiB slots, `ram_top`), A20M, and the reset alias of F0000h. Guest
  physical memory is 64 MiB at most.
- **Machine ports** of `fes_i386_cpu`: DDR port 0, MMIO, DMA, FLUSH, A20M,
  the attribute map and `cold_reset`, replacing the ideal fetch and data
  ports; retirement-trace outputs for stores, fetches, memory waits and
  replays.

### Uncached loads: replay, not a wait at M2

The design had an uncached load wait at M2 until it is the oldest. D to WB
only ever hold together, though: D's two forwarding tables, AG's late
operands and the store merge all count on it, so EX and WB cannot drain
under a held M2. Instead an uncached load waits a cycle in M2, then reads its
device only when nothing older can flush it or still has a store to make (EX and WB empty, or holding
only earlier non-store, non-branching, non-faulting uops of its own
instruction, and no interrupt being taken). One that reaches M2 behind
anything else takes no data and is marked `FAULT_REPLAY`: EX treats it as a
fault (it changes nothing) and WB restarts its instruction through the
reset path's `start`, after which D issues that instruction one uop at a time
(`serial`) so its loads come back as the oldest. Microcode writes nothing
architectural before its last uop that can fault, so restarting is safe
wherever a fault is. The design now says this
([memory types](../i386-cpu-design.md#memory-types),
[decision](../i386-cpu-design.md#decisions)).

The full lockstep found four more things the replay needed, each fixed here:

- **Loads whose data nothing uses must not read.** INT's and a far CALL's
  stack probes, ENTER's last check, POP m's pop into nothing, and the
  multiply and divide unit's LOAD and HI each reread or probe memory. On
  MMIO that is a device read the instruction does not make, and a probe that
  replays restarts a delivery. They carry `nodata` from D and touch nothing.
- **A replayed uop must not change EX's flags.** The replay mark now enters
  M2's record before `fes_i386_exctl` decides whether the uop may write
  flags, as a fault's does (ADC and SBB on MMIO read a stale CF otherwise).
- **CMPS's second load issues right behind its first** even in serial mode,
  since it takes the first load's result one stage ahead (`x_prev`).
- **Later loads of one instruction** (IRET's, POPA's, RETF's) count as the
  oldest behind its earlier loads, or the instruction would replay after its
  first load had already read the device and read it twice.

One case is left: ENTER with a nesting level writes its pushes before its
frame copies, so a copy from MMIO that restarts ENTER repeats the pushes
before it, with the same values. VGA writes are idempotent; the lockstep
compares the device's writes with the RTL's retired stores, which repeat
too.

### A Yosys bug the netlist found

The first netlist lockstep stopped on its first corpus file: DDR held FFh
where the retired stores had left 0. Comparing each new module's netlist
from the locked Yosys with its RTL, side by side on random inputs, every
output each cycle, found the bus interface's write buffer: an entry written
at `e_data[take0 ? tail1 + 2'd1 : tail1]` was never written when the
circular index wrapped. An array index is self-determined, so `tail1 + 2'd1`
with `tail1` = 3 is 0; the locked Yosys evaluates the sum at 32 bits, gets 4,
and drops the write. Reduced to `mem[b + 2'd1] <= data`, it is
[DeanoC/yosys#69](https://github.com/DeanoC/yosys/issues/69). The entry index
is now a 2-bit wire (`tail2`), and the README's synthesis notes say so. After
it the bus interface's, the L1I's and the L1D's netlists each match their RTL
over 4 million or more random cycles, and the old and new bus interface RTL
match each other over 6 million, so the RTL runs made before the change
stand. `fes_i386_decode` reads bytes at sums such as `byx[blen - 4'd1]`,
which stay in range, as the netlist lockstep has always covered.

### Not built in this slice

The L2, the TLBs and paging, the check of instructions in flight against
committed stores (self-modifying code past F2), critical-word-first fills,
and forwarding from the write buffer to a load that misses. The
[slice plan](../i386-cpu-design.md#memory-slices) orders them.

Three smaller things are known and left: a store takes its physical
address, A20M applied, as it enters WB, so an OUT to 92h or the 8042 that
changes A20 just ahead of it can leave that one store with the old mask (a
theoretical case; the boot did not meet it); a fetch in F2 the cycle after a
store commits into its line is not checked, since the L1I clears the line a
cycle later (slice 2's in-flight check covers it); and fetches from MMIO read
FFh rather than the device, as the benches did before.

### The first netlist

The slice as first built (`675fd13add`, netlist `658d014a`) placed at
27.47 MHz on nextpnr's estimate, against the base's 47.50. Its first route
converged at iteration 66 with a worst slack of -13.6 ns at 80 MHz (about
38 MHz; the base's seeds 1 and 2 were at -3.6 and -3.9 ns there). Timing repair then
hit [DeanoC/nextpnr#324](https://github.com/DeanoC/nextpnr/issues/324),
filed from the BCD slice: its re-negotiation sat at 4 to 10 overused wires
to the 2,000-iteration cap, and the router restored the pre-repair routing.
That route ends at 36.14 MHz ([nextpnr routes](#nextpnr-routes)). A route
that meets #324 takes one to two hours of a GPU instead of about 13 minutes,
with the same result.

The freeze was the cause. It reaches every enable from D to WB, and the
base drove it from registers: one LUT of six, each input a register. The
slice put the L1D in it. M2's `valid` waited on the tag compare of M10K
outputs, the valid bits' 128-way select by M2's set, and the uncached
load's `oldest` test of EX and WB; and the write buffer's entries waited on
`wb_store`, which waits on the freeze. The placed critical path, 36.4 ns:
`wb_s` through `oldest`, the L1D's `valid` and the freeze (14.8 ns), then
`wb_store` into the write buffer's coalescing logic and its 1,024 data
enables. Counted in LUT levels from a register or an M10K output, 6,801
flip-flop enables sat 9 to 13 deep; in the base four in five were 3 or less
and none more than 9.

### The cuts

None changes what a program sees, and the lockstep below ran on the result;
three cost cycles, as each says.

- **M1 compares the L1D's tags.** The lookup tags are read for AG's
  address as a uop enters M1, compared there with M1's physical page, and the
  hit registered for M2, with the set's valid bits beside it for the victim.
  A clear of the set drops both on the same edge; a fill re-reads M1's tags
  as it ends. M2 only selects the way.
- **The L1D's wait is one register** (`stall`), computed from the next
  cycle's state, so the freeze is again one LUT of six registers. A
  simulation check compared it with the old combinational `valid` on every
  cycle of the lockstep.
- **An uncached load waits a cycle in M2** and decides to read or replay
  then, from `oldest`, so the freeze never waits on that test. MMIO loads
  cost a cycle more.
- **The write buffer takes stores from a commit register** a cycle after
  they retire, so nothing in it waits on the freeze. Reads, DMA, FLUSH and
  I/O count the commit register as part of the buffer, so they may wait a
  cycle more. `st_wait` now counts the committing store as entries of its
  own, though it may coalesce.
- **The newest entry's line is kept in a register** for the coalescing
  compare, and **the L1I applies a store's snoop clear on the next edge**
  from a register, so their 1,024 and 512 enables wait on registers.

The cuts were found by counting LUT levels in the Yosys netlist, from a
register or M10K output to a flip-flop pin (a carry step counting 0.05),
grouped by register: the freeze's inputs went from 9 to 13 levels to one
LUT of registers, and the D to WB enables to 3 levels, as in the base. One more cut was built and not taken: F2's set
valid bits registered from their next state, which takes the L1I's
M10K-to-M10K address loop (a hit, `f2_advance`, the next block's address)
from 11 levels to 8 and passed the lockstep with a check that the register
always equals the bits. It would not move the CPU's figure, so it waits for
the front end's own slice:
- In Quartus, F1 and F2 average 104.2 and 105.8 MHz against Q's 101.3, and
  limit one seed of four. The cut is worth about half a MHz before Q
  ([Quartus](#quartus)).
- In nextpnr's routes, F1 averages 50.5 MHz, against D's 48.7 and MEM's
  48.9.

## The review fix

Two independent reviews of the slice, of its memory system and of its
pipeline, found three faults, all in M2's store merge. The merge was not
updated for the attribute map, MMIO or A20M this slice adds:

- **A store the memory system drops still reached the next load.** A store
  to read-only RAM or a hole goes nowhere, but a load within two cycles took
  its bytes. `MOV BYTE ES:[0], 55h` then `CMP BYTE ES:[0], 55h` found RAM in
  pc386's ROM at C0000h-C7FFFh and F0000h-FFFFFh, and in a hole: the probe a
  UMB scanner or memory sizing makes.
- **A device load took a store's bytes in place of the device's.** A load
  of a device byte, two bubbles behind a store to it, got the store's byte,
  from the store that retired as the load entered M2: the device was read,
  then the merge overwrote it. Ordinary VGA code does that, with the load's
  address from an ALU uop just before the store (`MOV BX, DI; MOV ES:[DI],
  AL; MOV AH, ES:[BX]`), and in planar modes a read differs from the byte
  written.
- **The merge compared linear addresses.** A store and a load through two
  aliases of one byte missed each other. Under A20M, a store through
  FFFF:0010h, then a load of 0000:0000h within three cycles, read the old
  byte. The reset alias at FFFF0000h is the same, and with paging so are
  double-mapped pages.

**The fix** (`c1b4a10db9`): M1 takes each distance between physical
addresses, A20M and the reset alias applied as the L1D and DDR apply them.
Each store's bytes that write RAM (`ram_bytes`) are worked out as it is in
EX, or in M2 for a MOVS element's, and carried with it to WB and to the
retired store. Only those bytes are taken. An access that crosses a 1 MiB
boundary under A20M, or into the reset alias, still compares the bytes past
the boundary as if they followed on; such a store then forwards nothing to
a load of its wrapped bytes.

**The lockstep's mixed memory.** The lockstep's MMIO device kept bytes like
RAM, and its map had no read-only RAM or holes, so none of the three could
show. The random programs and the memory cases now run with:
- read-only RAM at C0000h-C3FFFh and a hole at C4000h-C7FFFh beside the
  window, where the oracle's bus drops writes and the hole reads FFh;
- a device slot at B8000h-BBFFFh that reads back each byte XOR a hash of its
  address, on both sides.

The corpus keeps plain memory, as its expected final memory is a plain
RAM's. A random program whose stack or far pointers land in mixed memory
reads back a return address or flags image that is not its own. Its run
stops (`stray`) once its code leaves the program and the injected
interrupts' handler, once the instruction after one that read mixed memory
is not within 16 bytes on from it, or once TF is set: 1,929 of the lockstep's
32,000 runs (6.0%). The second rule came from a program whose IRET, after an
injected interrupt, popped one byte of its IP from the hole and landed
inside the program, on an x87 escape the program never had.

Mixed memory also showed a difference Bochs and the RTL already had. A
shift or rotate of a memory operand by zero writes the operand back on the
RTL, the byte it read, and Bochs logs that write but makes none. Plain
memory hid it, as the byte written back was the one stored. On a device the
write is visible, so the oracle takes the RTL's byte there. Whether a 386
makes that write cycle for a count of zero is not known here, and on VGA in
planar modes the write is not harmless; the design keeps it as an open
divergence ([Memory types](../i386-cpu-design.md#memory-types)).

**Forwarding cases.** Eight memory cases each store CL and load the byte
it wrote, twice in a LOOP so the second pass runs from the L1I and stores 1
over the first's 2. Each runs at 16 code alignments and with 0 to 3 NOPs
between the store and the load. They cover RAM, read-only RAM, a hole, the
device, the device with the load's address from INC BX or MOV BX, DI just
before the store, and an A20M alias, with and without A20M.

**Mutants of the fix:**

| RTL | What fails |
| --- | --- |
| No RAM check: every store byte forwards | read-only RAM, hole, and the device with a late address (both), at the first alignment and NOP count; 25 of 1,000 random programs (seed 1) |
| Linear distances, as before | the A20M alias: the load reads the first pass's 2 |

The device case without a late address does not fail under the first
mutant: its load never sits exactly two bubbles behind the store.

**Left as they were**, from the reviews:
- DMA from read-only RAM or a hole reads FFh, as the bus interface's comment
  says: the machine's ROMs are not DMA sources.
- A locked operation does not drain the write buffer, though the design
  said it would; with DMA the only other master, served in the buffer's
  order, nothing can see it. The design now says so.
- POPA writes each GPR as its load retires, so a restart repeats them with
  the same values; the design's rule that microcode writes nothing before
  its last uop that can fault now names it, beside ENTER.
- An L1I fill waits in its tag step while any store is in EX or WB, so a
  long REP STOS holds a fill. Performance only.
- A DIV or IDIV of a device operand always replays once (`own_load` turns
  down a divide), and serial issue after a replay runs to the end of the
  instruction, so a VGA-to-VGA REP MOVSB latch copy goes a uop at a time.

## Size

Yosys `238eac9a49`, `proc -norom; synth_intel_alm -family cyclonev
-nolutram`, of the routing spike's `spike_cpu`. The base is `b84add5c66`,
this branch before the slice, whose spike carried M10K models of the two
caches' arrays; the first build is `675fd13add`; this slice is `c4b9663d64`;
its review fix is `c1b4a10db9`.

| | Base | First build | This slice | Review fix | Change from the base |
| --- | ---: | ---: | ---: | ---: | ---: |
| LUTs (ALUT2-6) | 16,763 | 24,737 | 24,599 | 24,717 | +7,954 |
| Carry cells | 2,164 | 2,277 | 2,277 | 2,350 | +186 |
| Flip-flops | 9,901 | 13,413 | 13,779 | 13,776 | +3,875 |
| M10K | 25 (cache models and the microcode ROM) | 50 | 50 | 50 | +25 |
| nextpnr LUT cells (`MISTRAL_COMB`) | 19,030 (22%) | 27,130 (32%) | 27,000 (32%) | not placed | — |

The review fix adds 118 LUTs and 73 carry cells: the physical distances and
each store's RAM bytes in M1. Its deepest new register input is the EX
store's RAM bytes, 9.75 levels; the distances are 5.3 to 6.3. In Quartus
they reach 112 MHz or more on every seed.

The labelled registers put 3,241 flip-flops in the memory system's own
state (MEM: the bus interface with its commit register, the sequencers, both
L1s' valid bits), 381 more in M1 (the L1D's registers for M2, its hit and its
wait), 75 in EX (the store's physical lines, `st_wait`) and 28 in AG (the
lookup tags' read registers). Against the
[budgets](../i386-cpu-design.md#budgets): the L1I and L1D use 24 M10Ks each,
where the design gives the L1D, TLBs and write buffer 18 and the whole front
end 22. Each way's 128 × 14-bit tags take an M10K of their own, twice (the
lookup and the snoop or probe copy): packing a copy's four ways into one
56-bit row, two M10Ks, would save 8, at the cost of a read-modify-write per
fill. The valid bits in flip-flops with their per-set clears and the write
buffer's byte merges are most of the LUTs.

## The testbenches

- **Lockstep** (`lockstep_tb.cpp`): the CPU on `Port0`, a 128-bit port-0
  model added to [`pc386_ddr_model.h`](../../cores/fes-pc386/sim/pc386_ddr_model.h)
  with Kit A's port-0 latency ([#1076](https://github.com/DeanoC/fes/pull/1076)):
  18-19 clocks for most reads, 47-51 for the slowest 1%, a tail to 135, and
  refusals. The latency-free reruns use a fixed 18. Memory as retired stores
  leave it, from the new store trace, is what the lockstep compares; after
  every run, once the write buffer has drained, DDR must hold the same bytes.
- **MMIO window**: A0000h-BFFFFh is uncached for every corpus state and
  random program whose code keeps 16 bytes clear of it, through the oracle's
  `read`/`write` on the other side. Each instruction's device reads must be
  the oracle's, as a set; every store must reach the device once, in order,
  before any read of a later instruction. The random generator already gives
  DS, ES and SS random real-mode segments, so its loads, stores, strings,
  stacks and interrupt frames land in the window often.
- **Mixed memory** ([The review fix](#the-review-fix)): for the random
  programs and the memory cases, read-only RAM and a hole beside the window,
  and a device slot that reads back each byte XOR a hash of its address.
- **Latency-free gaps**: retirements within 16 cycles of a memory wait go to
  a `memory` bucket, so the cycle-exact hold checks still run on the rest.
- **pc386** (`machine_tb --cpu rtl`): the CPU's ports wired to the machine's
  MMIO, DMA and FLUSH ports, port 0 a `Port0` on the machine's pages, the
  attribute map pc386's. `sim/pc386_rtl_cpu.sv`, which exported the load
  size for the bench's own MMIO reads, is deleted.
- **Routing spike** (`spike_cpu`): the CPU with its caches, the machine's
  ports answered by stimulus bits and the attribute map tied to pc386's; the
  benchmark labels the new registers (MEM for the bus interface and the
  sequencers).
