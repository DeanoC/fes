# i386 far transfers and far pointer loads

Dated record, 2026-10-26. Host simulation and routed diagnostics on Powerboat.
No package, RBF or kit.

After [the stack slice](2026-10-26-i386-stack.md), the CPU gains the
real-mode far transfers and far pointer loads:
- JMP ptr16:16/32 (EAh) and CALL ptr16:16/32 (9Ah);
- JMP m16:16/32 (FFh /5) and CALL m16:16/32 (FFh /3);
- RETF (CBh) and RETF imm16 (CAh);
- LES, LDS, LSS, LFS and LGS.

They are fixed uop sequences, decoded without the microcode ROM, as the
design doc plans.

Run data: [`2026-10-26-i386-far.jsonl`](2026-10-26-i386-far.jsonl).
- The before figures are the stack slice after its review fix
  (`4e8eb2f7c4`, the stack record's "review" rows), which this slice merges.
- Routes and the full lockstep runs are of `465541e257`.
- A Quartus row's `fingerprint` is the first 12 hex digits of the SHA-256 of
  its `sources` map, as JSON with sorted keys.

## Sequences

**`dc` holds the uop to issue.** An instruction of several uops keeps its
place in `dc` while they issue. As D issues each but the last, `dc` takes the
next uop from `fes_i386_seq`, worked out from `dc` itself. So every field D
reads is a register at every step, and the uops issue one per cycle.
- CALL rel's two uops moved onto this first. D's step bit and its jump-uop
  select went, and the cycles and Yosys depth stayed the same.
- Each step changes only the fields that differ from the uop before. A field
  that holds is absorbed by DC's input select.
- One-bit controls are set outright at every step instead of held. A held
  one became an enable that Yosys built after D's issue, a level deeper.
- WB now moves EIP only at an instruction's last uop. A sequence that
  faults part way so leaves EIP at the instruction. Before this, a
  far-pointer load that faulted on its second uop had already moved EIP.

**Temporaries.** T0 (16 bits) and T1 (32) are destinations in RS_TEMP.
- WB writes them, and no forwarding sees them.
- A uop reads one at WB, or waits in D, on `t_busy`, until the uops writing
  it have retired.
- A temporary's load is 32 bits, so nothing merges into it. A first build
  merged a 16-bit offset into EAX's high half and raised spurious #GPs.

**Second segment destination.** A uop can write a segment register besides
its main destination (`seg2`), with the selector from T0 or from `c`.
- DC registers a one-hot mask of the segment registers each uop writes.
- D's segment-busy update is then one gate on issue.

| Instruction | Uops |
| --- | --- |
| LES, LDS, LSS, LFS, LGS | the selector's word into T0; the offset into the register, and WB writes the segment from T0 |
| JMP ptr16:16/32 | the far jump |
| CALL ptr16:16/32 | the probe; push CS; push the next EIP; the far jump |
| JMP m16:16/32 | the selector into T0; the offset into T1; the far jump, once they retire |
| CALL m16:16/32 | the selector into T0; the offset into T1; the probe, once they retire; push CS; push the next EIP; the far jump |
| RETF, RETF imm16 | the offset into T1 and the selector into T0, ESP unmoved; the far jump, once they retire, which steps ESP at WB |

- **The far jump** is one uop. AG computes its target as the new CS's base,
  selector × 16, plus the offset, through its address branch with no base or
  index looked up. WB writes CS, the selector reaching it in `c`.
- **Nothing is written before the offset check.** In 16-bit code an offset
  past FFFFh raises #GP(0) at the first uop that could write anything: the
  far jump, or a far call's probe.
- **RETF's ESP step.** WB adds the step to ESP. The jump is always taken and
  flushes every younger uop, so nothing needs the new ESP sooner.

## What the 386EX does

The corpus, with Bochs agreeing, decided the first three. Random programs
and the 386 manual decided the fourth, where Bochs also leaves ESP
unchanged.
- **A far pointer's two parts are checked separately.**
  - The selector's offset wraps at 64 KiB in 16-bit addressing: a pointer at
    FFFEh reads its selector at 0000h.
  - 0FB2#1890 passes at FFFEh; 0FB2#58 raises #GP for the offset word at
    FFFFh.
  - So there is no whole-operand check, which a first build had.
- **A 32-bit far call pushes CS as a zero-extended dword** (8 bytes in all).
  A 32-bit PUSH CS writes only the word.
- **A 32-bit RETF checks the selector's slot as four bytes.** 66CB#2041:
  ESP FFF9h raises #SS, though the selector's word, at FFFDh, fits.
- **A far call writes nothing when its second push would cross the stack's
  limit.**
  - Random programs found it: SP 3, two 2-byte pushes, the second at FFFFh.
  - The 386 manual's "stack not large enough for the return address" check
    agrees. The lockstep holds the RTL to writing nothing on a fault.
  - So a far call starts with a probe: a read of the return address's lower
    slot, which checks its limit. The push of CS then checks the higher slot
    as the first write.

**nextpnr averages 71.2 MHz against 70.4.**
- **Worst paths:**
  - Seed 1: D's displacement for a far pointer's selector, the offset plus
    the operand size (`dc` → `ag_disp`, a 32-bit carry chain, 19 cells).
    Moving that sum into DC, or into AG's rows, is the next cut here.
  - Seeds 3 and 4: D's issue into `dc` (`dc` → `dfwd.ag_sp`/`ag_early`/`in_ag`
    → `advance` → `dc_valid` → `dc`, 7 cells). The sequencer made `dc`'s
    input select a three-way one.
  - Seed 2: Q's own loop, as before.
- **By stage:** D 69.4-77.4 MHz against 71.4-75.4, and DC 70.0-75.8 against
  70.4-77.9.
- **An earlier route** of this slice, at `def39756e9` before it merged the
  review fix, gave 71.20, 74.67, 71.86 and 72.86. The fix's WB stop on D's
  issue cost D and DC a Yosys level each here, so this slice drops it (see
  below).

**Quartus averages 101.8 MHz against 101.3,** Q-limited on every seed.

**Yosys's depth matches the stack slice's:** D 8, DC 10, EX 10, M1 7, M2 7,
WB 6. Its runs move by a level between ABC runs, in stages with no RTL
change too.

**The review fix, merged.** The stack slice's review fix (an out-of-limit
32-bit CALL rel faults before its push; a faulting branch does not redirect;
nothing issues, fetches or reads after a fault) came in with the merge of
`deano/i386-stack`.
- Its CALL check now keys on the sequencer's first CALL step.
- D's issue keeps `halted` but drops WB's stop. WB's flush already clears
  what D issues in the fault cycle. The stop put WB's decode ahead of DC's
  and D's loads, at DC 11 and D 9 in Yosys, and 10 and 8 without it. The
  three directed fault checks pass either way.
- Fetch requests and data reads keep WB's stop.

## Cycle costs

Without latency, measured on corpus states as cycles from start to HLT,
against a NOP's 17. A taken transfer's figure includes the redirect: 10
cycles over the instruction's own, which is why a taken branch retires 11
cycles behind the one before.

| Instruction | Extra cycles | Near or one-uop equivalent |
| --- | --- | --- |
| LES and its kin | 1 | MOV r, m: 0 |
| JMP ptr | 10 | JMP rel: 10 |
| CALL ptr | 13 | CALL rel: 11 |
| RETF | 17 | RET: 10 |
| JMP m16:16 | 17 | JMP r/m: 10 |
| CALL m16:16 | 20 | |

RETF and the indirect forms pay about 5 cycles for the wait on T0 and T1.

**Corpus.** 75,000 new states: the 11 stems with their 66h and 67h forms. The
register forms of the memory-only instructions raise #UD.

**Random programs** pick their state first and pass the program's linear
base to the layout, so a far target is a CS:IP for its target's linear
address.
- The selector is 800h paragraphs below the target's, so the offset stays
  near 8000h, and the code after it runs well inside CS.
- A third of CALL blocks are far:
  - CALL ptr, or CALL m16:16/32 through a pointer that two MOVs store just
    before;
  - returning with RETF, or RETF imm16 at the outer level.
- Far JMPs, direct or indirect, skip 0-3 instructions. Code after one runs
  with the new CS.
- LES and its kin are a random memory form. LSS stays out of subroutine
  bodies.
- An indirect far call inside a subroutine stores its pointer at a random DS
  offset, the one memory write a body may make. It could land on an
  enclosing return address; none of the 32,000 programs did.
- The random trace differs from the stack slice's, as the generator's mix
  changed. 15.3M retirements against 15.8M.

**Holds.** The stack-after-stack hold leaves out CALL ptr and RETF, which are
several uops, as it does CALL rel.

Mutations, each on 3,500 corpus states (seven far stems) and 2 × 200 random
programs, of `def39756e9`:

| Mutation | Result |
| --- | --- |
| D does not wait for T0 and T1 | 1,447 corpus states and 213 of 400 programs fail |
| D's segment-busy vector ignores the second destination | 80 of 400 programs fail; the latency-free trace changes (the corpus passes) |
| D does not check the far offset | 22 corpus states fail (the random programs' offsets stay small) |

## What the design doc should say

This is reported for the doc's owner to write; the doc is unchanged here.

- **Prediction.** Far transfers are plain taken branches for now, with no BTB
  or return stack, at the costs above.
- **A far call's first uop is a stack probe.** It makes the "stack not large
  enough" check before anything is written.
- **Six-byte operands.** The design doc's two accesses are two uops through
  the temporaries. Each part is checked on its own, except RETF's selector
  slot, which is operand-sized.
- **Latency table.** LES and its kin cost one cycle over a load. A one-load
  16-bit form is a later option: the 4 bytes fit one access, and the high
  half would come from `pipe.ld`.
- **Clock.** The sequencer puts D's issue into `dc`'s three-way input
  select, and a far pointer's selector displacement is a carry chain in D.
